# 小游戏接入指南

这篇文档写给想在房间里接小游戏的人。看完你应该能：建一个 playroom，跑起一局游戏，把每一步动作同步给房间里的所有人，并且知道哪些事会被服务端拦下来。

## 先搞清楚房间类型

房间有两个类型：`workroom` 和 `playroom`，字段名就是 `type`。建房时指定，不传默认是 `workroom`。

- `workroom` 是干活的地方，能发 `intent=task` 的消息。
- `playroom` 是玩的地方，发 `intent=task` 的消息会被服务端拒绝。

想改类型，调：

```
POST /api/rooms/:id/type
body: {type}
```

`type` 只能是 `workroom` 或 `playroom`。在 `playroom` 里发 `intent=task`，服务端返回 HTTP 400，body 是：

```json
{"error":"ROOM_TYPE_FORBIDDEN"}
```

所以小游戏相关的消息，别带 `intent=task`，否则自己把自己拒了。

## 人数上限和限流

三个环境变量控制容量和频率，启动时读，值不合法直接启动失败，不会带着错配置跑起来：

- `ROOM_MAX_MEMBERS_WORKROOM`，默认 50。
- `ROOM_MAX_MEMBERS_PLAYROOM`，默认 200。
- `GAME_BROADCAST_THROTTLE_MS`，默认 500。

`GAME_BROADCAST_THROTTLE_MS` 是游戏状态广播的最小间隔，单位毫秒。你一秒里狂推状态，服务端会按这个值合并广播。写小游戏时别指望每帧都发，按这个节奏来。

## 游戏会话存在哪

新建了一张表 `game_sessions`：

```
id TEXT PRIMARY KEY
room_id TEXT NOT NULL
game TEXT NOT NULL
phase TEXT NOT NULL DEFAULT 'lobby'
state TEXT NOT NULL DEFAULT '{}'
updated_at INTEGER NOT NULL
```

- `id` 是这一局游戏自己的 id。
- `room_id` 是它属于哪个房间。
- `game` 是游戏名，比如你写的是 `gomoku`，就填 `gomoku`。
- `phase` 是阶段，默认 `lobby`。开局前是 `lobby`，玩起来你自己定义后续阶段名，比如 `playing`、`settled`。
- `state` 是这一局的完整状态，字符串，默认 `{}`。你自己决定里面放什么，序列化成字符串存。
- `updated_at` 是最后更新时间，整数，秒或毫秒你自己在业务里统一，别一会儿秒一会儿毫秒。

一局游戏的生命周期就靠 `phase` 和 `state` 两个字段表达，服务端不替你想游戏逻辑。

## 实时同步：用 WS 的两个新帧

WebSocket 帧类型新增两个：`game_action` 和 `game_state`。

`game_action` 是玩家操作，客户端发上来：

```
{game: string, seat?: string, action?: unknown}
```

`game_state` 是服务端广播的局面，发下去给房间所有人：

```
{game: string, seat?: string, state?: unknown, state_hash?: string}
```

字段说明：

- `game`：游戏名，和 `game_sessions.game` 对上。
- `seat`：座位号，可选。单人游戏不用管，多人对抗类用得上。
- `action`：玩家做了什么，形状你自己定，服务端不解析。
- `state`：完整局面，形状你自己定。
- `state_hash`：局面的哈希，用来让客户端快速判断“我这边的局面是不是最新”。

流程一般是：玩家点了棋盘，客户端发一个 `game_action` 上去；你的游戏服务算出新局面，写进 `game_sessions.state`，然后把 `game_state` 广播给房间。`state_hash` 带上新局面的哈希。客户端收到 `game_state` 后，先比 `state_hash`，一样就跳过，不一样才重绘。

## 座位和人设

`room_members` 表新增了 `persona_role TEXT` 列，用来标记这个成员在这个房间里演什么角色。给小游戏玩家配角色，调：

```
POST /api/rooms/:id/persona
body: {persona_id, role}
```

`role` 写进 `persona_role`。小游戏里可以拿它判断谁是裁判、谁是选手。

## 看房间统计

想知道房间里现在什么情况，调：

```
GET /api/rooms/:id/stats
```

拿回来的是这个房间的汇总数据，人数、类型这些。具体字段以接口返回为准，别在客户端硬编码不存在的字段。

## 兼容老客户端

协议版本升到 v1.3。老客户端不认识 `game_action` 和 `game_state`，按约定会忽略未知帧类型。所以你接小游戏时，不必担心老版本客户端收到新帧会崩。反过来，你的新客户端也要忽略自己不认识的帧，别一收到没见过的类型就报错断开。

## 一个最小接入顺序

1. 建 `playroom`：`POST /api/rooms/:id/type`，body `{type: "playroom"}`。
2. 确认人数上限没超 `ROOM_MAX_MEMBERS_PLAYROOM`。
3. 建游戏会话，`game_sessions` 插一行，`game` 填你的游戏名，`phase` 用 `lobby`。
4. 玩家坐下后，用 `POST /api/rooms/:id/persona` 把 `persona_role` 写上。
5. 玩家操作走 `game_action` 上来，服务端算完局面，更新 `game_sessions.state` 和 `updated_at`，再用 `game_state` 广播，带 `state_hash`。
6. 广播别超过 `GAME_BROADCAST_THROTTLE_MS` 的节奏。
7. 房间状态用 `GET /api/rooms/:id/stats` 查。

照这个顺序接，基本不会踩到类型和限流的坑。真被 `ROOM_TYPE_FORBIDDEN` 拒了，先检查你发消息时是不是带了 `intent=task`。
