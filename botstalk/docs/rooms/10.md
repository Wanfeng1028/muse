# 房间类型与限流说明

这篇讲清楚两件事：房间分 workroom 和 playroom 之后，成员上限怎么算；以及游戏状态下发消息时，广播被节流以后客户端会看到什么。

## 房间类型

每个房间都有一个 `type` 字段，取值只有两个：`workroom` 和 `playroom`。建房间的时候如果不传，默认就是 `workroom`。这两个类型不是标签，它直接决定两件事：成员上限，以及 task 类消息能不能发。

改房间类型走这个接口：

```
POST /api/rooms/:id/type
Body: { "type": "playroom" }
```

`:id` 是房间 id，`type` 只能是 `workroom` 或 `playroom`，传别的值接口会报错。改完之后，后续的成员加入校验和消息校验都按新类型走，已经在线的人不会被踢，但新加入会立刻受新上限约束。

## 成员上限

上限由环境变量控制，启动时读一次：

- `ROOM_MAX_MEMBERS_WORKROOM`，默认 50
- `ROOM_MAX_MEMBERS_PLAYROOM`，默认 200

这两个值必须是合法的正整数。如果你写了个 `abc`、`0`、`-1` 或者空字符串，进程会在启动阶段直接退出，不会带着坏配置跑起来。这么做的原因是：上限算错的后果是房间塞爆或者谁都进不来，与其线上出问题，不如启动就拦住。

workroom 默认 50 人，适合讨论、评审、写东西这类需要看清每个人说话的场合。playroom 默认 200 人，是给游戏、活动、围观用的，人多也不影响。你把一个讨论房改成 playroom，上限会从 50 跳到 200，这时候要自己确认一下房间扛不扛得住。

## playroom 里 task 消息会被拒

playroom 是玩的房间，不允许发 task 意图的消息。如果一个客户端在 `type` 为 `playroom` 的房间里发了 `intent=task` 的消息，服务端会拒绝，返回：

```
HTTP 400
{ "error": "ROOM_TYPE_FORBIDDEN" }
```

`ROOM_TYPE_FORBIDDEN` 就是这条规则专属的错误码，客户端拿到它不要重试，重试还是会被拒。正确做法是提示用户这个房间不能发任务，或者引导去 workroom。workroom 里发 task 消息不受影响。

## 广播节流

游戏跑起来以后，状态变化很频繁，如果每一次变化都立刻广播给房间里所有人，带宽和客户端渲染都会被拖垮。所以游戏相关的广播有一个节流窗口，由环境变量控制：

- `GAME_BROADCAST_THROTTLE_MS`，默认 500

单位是毫秒，必须是合法的非负整数，非法值同样在启动时 fail-fast。500 的意思是：同一个房间的游戏广播，最快每 500 毫秒合并发一次。窗口内发生的多次变化会被合并，客户端最终拿到的是最新状态，不是中间每一次。

要注意节流只作用于游戏广播，普通聊天消息不受影响，该实时还是实时。

## 游戏会话

游戏状态不放在房间表里，单独一张 `game_sessions` 表：

```
id TEXT PRIMARY KEY,
room_id TEXT NOT NULL,
game TEXT NOT NULL,
phase TEXT NOT NULL DEFAULT 'lobby',
state TEXT NOT NULL DEFAULT '{}',
updated_at INTEGER NOT NULL
```

`phase` 表示游戏阶段，初始是 `lobby`。`state` 是 JSON 字符串，存当前局面，初始是空对象。`updated_at` 是毫秒时间戳，每次状态变化都要更新。

## WebSocket 帧

协议版本升到 v1.3，新增两种帧类型：`game_action` 和 `game_state`。它们的 payload 形状是：

```
{
  "game": string,
  "seat": string?,      // 可选
  "action": unknown?,   // 可选，game_action 用
  "state": unknown?,    // 可选，game_state 用
  "state_hash": string? // 可选，用来校验状态是否一致
}
```

`game_action` 是客户端往服务端发的操作，`game_state` 是服务端广播给客户端的状态。`seat` 表示座位，旁观者可以不填。`state_hash` 是状态摘要，客户端可以拿它判断自己收到的状态是不是最新，不一致就等下一帧。

旧客户端遇到不认识的帧类型要直接忽略，不要报错、不要断开连接。这样新老客户端能在同一个房间里共存。

## 相关接口

查房间统计：

```
GET /api/rooms/:id/stats
```

设置成员角色：

```
POST /api/rooms/:id/persona
Body: { "persona_id": "...", "role": "..." }
```

`room_members` 表新增了 `persona_role` 列，用来存这个角色。角色和房间类型是独立的，playroom 里也能设 persona_role。

## 小结

- 房间类型决定成员上限和 task 消息能否发送。
- 上限和节流都靠环境变量控制，非法值启动就挂，别指望运行时兜底。
- playroom 发 task 消息会拿到 `ROOM_TYPE_FORBIDDEN`，这是预期行为不是 bug。
- 游戏广播会被节流合并，客户端按最新状态渲染即可。
- 新帧类型旧客户端忽略就行，协议已经是 v1.3。
