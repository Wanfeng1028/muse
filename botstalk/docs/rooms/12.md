# 房间类型-安全说明

这篇讲房间类型跟安全相关的那些事。读完你应该能搞清楚三件事：房间类型是怎么定的，哪些操作会被拦，出错了怎么排查。

## 房间类型是什么

房间创建的时候要指定一个 type，取值只有两个：`workroom` 或者 `playroom`。不传的话默认是 `workroom`。

数据库里 `rooms` 表加了 `type` 列，类型是 `TEXT NOT NULL DEFAULT 'workroom'`。也就是说老房间升级之后自动变成工作间，不需要你手动改数据。

创建之后想改类型，走这个接口：

```
POST /api/rooms/:id/type
```

body 里带 `{type}`，值是 `workroom` 或 `playroom`。

## 两种房间的差别

`workroom` 是干活的地方，默认最多 50 人，由环境变量 `ROOM_MAX_MEMBERS_WORKROOM` 控制。

`playroom` 是玩的地方，默认最多 200 人，由环境变量 `ROOM_MAX_MEMBERS_PLAYROOM` 控制。

这两个环境变量的值如果填了非法内容（比如负数、非数字、空字符串），服务启动时会直接失败，不会带着错配置跑起来。这是故意的，宁可起不来也别带病上线。

## 核心拦截规则

最需要记住的一条：**在 playroom 里，intent=task 的消息会被拒绝**。

返回的 HTTP 状态码是 400，JSON 内容是：

```json
{"error":"ROOM_TYPE_FORBIDDEN"}
```

为啥要拦？因为 playroom 是给游戏、闲聊、放松用的。如果有客户端往 playroom 里塞任务类消息，说明要么客户端逻辑有问题，要么有人在拿 playroom 绕开工作流的限制。不管哪种，直接拒掉最干净。

`ROOM_TYPE_FORBIDDEN` 这个错误码是固定的，客户端应该按它做分支处理，别去匹配错误文案。

## 成员和角色

`room_members` 表加了 `persona_role TEXT` 列，用来记这个人在房间里以什么角色参与。

给成员设置角色走：

```
POST /api/rooms/:id/persona
```

body 是 `{persona_id, role}`。这个接口不改房间类型，只管人跟角色的绑定关系。

## 游戏会话

playroom 里通常会跑游戏。游戏状态存在 `game_sessions` 表：

- `id`：主键
- `room_id`：属于哪个房间
- `game`：游戏标识
- `phase`：阶段，默认 `lobby`
- `state`：状态内容，默认 `{}`
- `updated_at`：更新时间戳

WebSocket 那边新增了两种帧类型：`game_action` 和 `game_state`。

`game_action` 是客户端往上发的动作，`game_state` 是服务端往下推的状态。

payload 的形状是：

```
{game: string, seat?: string, action?: unknown, state?: unknown, state_hash?: string}
```

`game` 必填，`seat` 是座位号，`action` 是动作内容，`state` 是状态快照，`state_hash` 用来校验状态有没有被改过。

服务端推 `game_state` 的时候有节流，默认 500 毫秒一次，由 `GAME_BROADCAST_THROTTLE_MS` 控制。这个值非法的话同样是启动时 fail-fast。节流是为了防止高频状态更新把连接打爆。

## 兼容性

老客户端不认识 `game_action` 和 `game_state` 这两种帧，会直接忽略。这是设计好的，不会因为收到未知帧就崩。

协议版本升到了 v1.3，客户端可以按版本号判断服务端支不支持房间类型这套东西。

## 统计接口

想看房间的实时情况：

```
GET /api/rooms/:id/stats
```

返回房间相关的计数信息，用来做面板或者监控都行。

## 排查清单

遇到问题时按这个顺序看：

第一，确认房间的 `type` 到底是什么。是 `workroom` 还是 `playroom`，决定了后面的行为。

第二，如果收到 `ROOM_TYPE_FORBIDDEN`，检查发消息的 intent 是不是 `task`，以及房间是不是 `playroom`。这两条同时成立才会触发。

第三，如果是人数超了，看房间类型对应的环境变量值，别只看默认值。

第四，如果是游戏状态不同步，先看 `GAME_BROADCAST_THROTTLE_MS`，再对比 `state_hash` 确认状态是不是真的一致。

第五，服务起不来，优先查那两个成员上限变量和节流变量是不是填了非法值。

## 一句话总结

房间类型把干活和玩分开了，`playroom` 里不准发 `intent=task`，违者返回 `ROOM_TYPE_FORBIDDEN`。环境变量填错就起不来，这是好事。老客户端忽略新帧，协议到 v1.3。
