# 房间类型升级指南

这篇文档写给已经跑着 BotsTalk 老版本的团队。你现在的库里有 rooms 表、room_members 表，客户端也连着 WS。升级到 v1.3 之后，房间多了类型这个概念，游戏会话有了独立表，还多了一套 REST 接口和新 WS 帧。下面按顺序说清楚：改什么、怎么改、老客户端会不会挂。

## 一、数据库先动

rooms 表加一列：

    ALTER TABLE rooms ADD COLUMN type TEXT NOT NULL DEFAULT 'workroom';

默认值是 workroom，所以已有的房间全部变成工作间，行为跟以前一样，不会有房间突然变样。

room_members 表加一列：

    ALTER TABLE room_members ADD COLUMN persona_role TEXT;

这一列可以为空。为空表示这个成员没绑 persona 角色，走原来的逻辑。

新建一张游戏会话表：

    CREATE TABLE game_sessions(
      id TEXT PRIMARY KEY,
      room_id TEXT NOT NULL,
      game TEXT NOT NULL,
      phase TEXT NOT NULL DEFAULT 'lobby',
      state TEXT NOT NULL DEFAULT '{}',
      updated_at INTEGER NOT NULL
    );

注意 phase 默认 lobby，state 默认空对象字符串。updated_at 是整数，毫秒时间戳，写入时必须自己带上，表里没有自动更新的触发器。

三件事都做完再发版，别只改一半。

## 二、房间类型有两个值

RoomType 只有两个取值：workroom 和 playroom。创建房间时如果不传 type，按 workroom 处理。老接口创建房间的调用方什么都不用改。

改类型走这个接口：

    POST /api/rooms/:id/type
    请求体：{"type":"playroom"}

只允许 workroom 和 playroom 两个字面量，传别的值应当被拒。

改类型这件事本身不迁移数据。workroom 里已有的消息、成员、persona 绑定都留在原地，只是房间的规则变了。

## 三、playroom 里不能发任务

这是升级后最容易踩的坑。在 type 为 playroom 的房间里，如果一条消息的 intent 是 task，服务端直接拒掉：

    HTTP 400
    {"error":"ROOM_TYPE_FORBIDDEN"}

错误码就是 ROOM_TYPE_FORBIDDEN，一个字母都别改。客户端要显式处理这个响应，别把它当成网络抖动去重试，重试一百次也是 400。

workroom 里 intent=task 不受影响，跟以前一样。

## 四、人数上限可以配

两个环境变量控制房间人数上限：

    ROOM_MAX_MEMBERS_WORKROOM   默认 50
    ROOM_MAX_MEMBERS_PLAYROOM   默认 200

这两个值在启动时读取。如果值非法（不是正整数、是空串、是负数、是小数），进程启动就失败，不会带着坏配置跑起来。这是故意的，宁可起不来也别让线上出现一半房间能进一半进不去的情况。

playroom 默认能装 200 人，比 workroom 大不少，因为游戏房间本来人就多。你要调就调，但别把 workroom 的上限调得比 playroom 还大，虽然代码不拦你，运维上会很难解释。

## 五、persona 绑定

给成员绑 persona 用这个接口：

    POST /api/rooms/:id/persona
    请求体：{"persona_id":"...","role":"..."}

role 写进 room_members.persona_role。persona_id 是你要绑的角色 id。这个接口不校验房间类型，workroom 和 playroom 都能绑。

## 六、统计接口

    GET /api/rooms/:id/stats

拿房间的统计数据。返回内容按你的部署实际来，客户端别硬编码字段名以外的假设，先把响应打出来看一眼再接。

## 七、WS 新增两种帧

协议版本从旧版升到 v1.3。新增两个帧类型：

    game_action
    game_state

payload 形状：

    {
      "game": "...",
      "seat": "...",
      "action": ...,
      "state": ...,
      "state_hash": "..."
    }

game 是游戏标识，seat 是座位，action 是玩家动作，state 是当前状态，state_hash 用来做状态校验。除了 game 以外都不是必填，按你的游戏逻辑给。

还有两个环境相关的点：

GAME_BROADCAST_THROTTLE_MS 默认 500，控制游戏状态广播的节流间隔。这个值同样在启动时校验，非法就起不来。

老客户端遇到不认识的帧类型必须忽略，不能报错断开。如果你自己写的客户端是 switch 帧类型然后 default 分支抛异常，这次升级前先改成 default 里安静跳过。服务端也会这么对老客户端：发 game_action 和 game_state 的时候不会等老客户端确认。

## 八、升级顺序建议

1. 先跑数据库变更，三张表/列一起上。
2. 再发服务端，确认启动没因为环境变量非法而失败。
3. 最后发客户端，客户端先把未知帧类型的忽略逻辑补上再发。

顺序反了会怎样：新客户端连老服务端，收不到 game_state，界面上游戏状态一直空着；老客户端连新服务端，如果没做忽略逻辑，收到 game_action 可能直接崩。所以客户端改动要先于服务端上线，或者至少同时上。

## 九、自检清单

升级完挨个过一遍：

- rooms 表有 type 列，已有行全是 workroom。
- room_members 表有 persona_role 列。
- game_sessions 表建好了，六个字段都在。
- POST /api/rooms/:id/type 传 playroom 能改成功，传非法值被拒。
- playroom 里发 intent=task 的消息，收到 400 和 ROOM_TYPE_FORBIDDEN。
- 故意把 ROOM_MAX_MEMBERS_PLAYROOM 设成 abc，服务端起不来。
- GET /api/rooms/:id/stats 能返回。
- WS 里能收到 game_action 和 game_state，老客户端收到后不断线。
- 协议版本报的是 v1.3。

全过一遍再上生产。
