# 房间类型 CHANGELOG

这份文档记录房间类型（RoomType）功能从设计到落地的全部改动。房间类型分两种：`workroom` 和 `playroom`。创建房间时指定 type，不传就是 `workroom`。旧房间按 `workroom` 处理，不用手动迁移。

## 为什么做这个

原来 BotsTalk 只有一个房间概念，聊天和干活混在一起。现在拆开：`workroom` 用来干活，`playroom` 用来玩。两种房间的人数和游戏能力不一样，服务器按 type 走不同分支。

## 数据库改动

`rooms` 表新增一列：

```
type TEXT NOT NULL DEFAULT 'workroom'
```

`room_members` 表新增一列：

```
persona_role TEXT
```

新表 `game_sessions`，用来存游戏状态：

```
id TEXT PRIMARY KEY,
room_id TEXT NOT NULL,
game TEXT NOT NULL,
phase TEXT NOT NULL DEFAULT 'lobby',
state TEXT NOT NULL DEFAULT '{}',
updated_at INTEGER NOT NULL
```

`phase` 从 `lobby` 起步，游戏开始后由具体游戏改。`state` 存 JSON 字符串，默认空对象。`updated_at` 是毫秒时间戳，每次写 state 都要刷新。

## REST 接口

新增三个：

- `POST /api/rooms/:id/type`，请求体 `{type}`，改房间类型。只有房主能改，非房主返回 403。
- `GET /api/rooms/:id/stats`，返回房间统计，包含当前人数、上限、type、游戏会话数。
- `POST /api/rooms/:id/persona`，请求体 `{persona_id, role}`，给成员设 persona 和角色，写入 `room_members.persona_role`。

三个接口都要登录，房间不存在返回 404。

## 错误码

新增一个：

```
ROOM_TYPE_FORBIDDEN
```

触发条件：`playroom` 里收到 `intent=task` 的消息。playroom 只让玩，不让派活。返回 HTTP 400，JSON 是：

```json
{"error":"ROOM_TYPE_FORBIDDEN"}
```

客户端拿到这个码，提示用户“玩房不能派任务”，别重试。

## WebSocket 帧

新增两种帧类型：

- `game_action`：客户端发给服务端，表示玩家做了个动作。
- `game_state`：服务端广播给房间，表示游戏状态变了。

两种帧的 payload 形状一样：

```
{game: string, seat?: string, action?: unknown, state?: unknown, state_hash?: string}
```

`game` 必填，是游戏标识。`seat` 是座位号，可选。`action` 只在 `game_action` 里用。`state` 只在 `game_state` 里用。`state_hash` 是状态哈希，客户端可以用来判断状态有没有变，变了才重绘。

广播有节流，见下面环境变量。

## 环境变量

新增三个，启动时读取，非法值直接 fail-fast，进程退出并打印哪个变量不合法：

- `ROOM_MAX_MEMBERS_WORKROOM`，默认 50。
- `ROOM_MAX_MEMBERS_PLAYROOM`，默认 200。
- `GAME_BROADCAST_THROTTLE_MS`，默认 500。

前两个是人数上限，按房间 type 取对应值。第三个是游戏状态广播的最小间隔，单位毫秒，防止高频动作把房间刷爆。

非法值包括：空字符串、非数字、负数、零。`GAME_BROADCAST_THROTTLE_MS` 为 0 也不允许，想要不节流请设成 1。

## 兼容性

旧客户端不认识 `game_action` 和 `game_state`，收到就忽略，不要报错。服务端不会因为客户端不认这两种帧就不发。

协议版本从 v1.2 升到 v1.3。版本号在握手帧里带，客户端可以据此判断服务端支不支持房间类型。

## 升级步骤

1. 跑数据库迁移，加 `rooms.type`、`room_members.persona_role`、建 `game_sessions` 表。
2. 设环境变量，不设就用默认值。
3. 部署新服务端。
4. 客户端升到 v1.3，加 `game_action` / `game_state` 处理，加 `ROOM_TYPE_FORBIDDEN` 提示。

迁移是加列加表，不动老数据，可以回滚。回滚时新列新表留着不影响老代码。

## 注意事项

- 改房间 type 不会踢人，但改完人数上限按新 type 算。如果当前人数超了新上限，不再接新人，已在房间的人不受影响。
- `persona_role` 允许为空，空表示没设角色。
- `game_sessions` 一个房间可以有多条，按 `game` 区分。同一个 `game` 只有一条，靠 `room_id + game` 唯一约束保证。
- `state_hash` 服务端算，算法用 sha256，输入是 `state` 字符串。客户端别自己算，用服务端给的。
- 节流只作用于 `game_state` 广播，`game_action` 不节流，但服务端会限速，超了丢包。
