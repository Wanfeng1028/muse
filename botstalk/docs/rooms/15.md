# 房间类型测试报告模板

这份模板是给测试同学填的。房间类型这块从提出到上线一共改了三处：rooms 表加列、REST 加接口、WS 加帧。测试结论要能对上契约，别只写“测试通过”。

## 一、基本信息

- 报告人：
- 测试日期：
- 分支 / commit：
- 环境：本地 / 预发 / 生产
- 协议版本：必须是 v1.3，低于这个版本的客户端按旧逻辑走，未知帧类型直接忽略

## 二、环境变量检查

启动服务前把这三个变量配好，非法值要在启动阶段就挂掉，不能等到运行时才报错：

- ROOM_MAX_MEMBERS_WORKROOM，默认 50，正整数
- ROOM_MAX_MEMBERS_PLAYROOM，默认 200，正整数
- GAME_BROADCAST_THROTTLE_MS，默认 500，正整数

要测的场景：不配这三个变量时用默认值起服务；配成 0、负数、空串、非数字字符串，服务必须 fail-fast，日志里写清楚是哪个变量不合法。这一条漏测过，之前线上出现过配成字符串还硬启的情况。

## 三、表结构核对

- rooms 表存在列 type，类型 TEXT，NOT NULL，DEFAULT 'workroom'。已有房间升级后 type 应该是 workroom。
- room_members 表存在列 persona_role，类型 TEXT，可为空。
- game_sessions 表字段：id TEXT PRIMARY KEY、room_id TEXT NOT NULL、game TEXT NOT NULL、phase TEXT NOT NULL DEFAULT 'lobby'、state TEXT NOT NULL DEFAULT '{}'、updated_at INTEGER NOT NULL。六个字段一个都不能少，默认值要实测，光看建表语句不算数。

## 四、REST 接口

1. POST /api/rooms/:id/type，body 是 {type}。合法值只有 workroom 和 playroom。传别的值返回 400。房间不存在返回 404。调用者没权限也要单独记一条。

2. GET /api/rooms/:id/stats。返回里要能区分房间类型，playroom 和 workroom 的成员上限不一样，stats 要跟实际配置对上。

3. POST /api/rooms/:id/persona，body 是 {persona_id, role}。写完要回查 room_members 的 persona_role 是不是落库了，别只看接口返回 200。

错误码单独测一条：playroom 里发 intent=task 的消息，必须返回 HTTP 400，body 是 {"error":"ROOM_TYPE_FORBIDDEN"}。这条要断言状态码和完整 JSON 两个点，只断言状态码不算数。

## 五、WS 帧

新增 game_action 和 game_state 两种帧。payload 形状：{game: string, seat?: string, action?: unknown, state?: unknown, state_hash?: string}。

要测：

- 发 game_action，服务端按 GAME_BROADCAST_THROTTLE_MS 节流广播，500ms 内连发多条不能全放出去。
- 发 game_state，带 state_hash，客户端收到的 state_hash 要和发的对得上。
- 旧客户端收到未知帧类型要忽略，不能崩，也不能把连接断掉。这条要真拿旧版本客户端跑一遍。

## 六、房间类型默认值

创建房间不传 type 时，落库必须是 workroom。playroom 要显式传。成员上限按类型取对应环境变量，workroom 到 50 就拒，playroom 到 200 才拒。边界值卡在 50 和 51、200 和 201 各测一次。

## 七、回归范围

- 老房间升级后 type 和 persona_role 都不能丢数据。
- 房间列表、成员列表、邀请流程不受 type 列影响。
- 协议版本 v1.3 之前的老客户端连上来，除未知帧忽略外，原有功能照常。

## 八、结论

按上面每一项填“通过 / 不通过 / 未测”，不通过的要贴请求、响应、日志三段证据。最后给一句整体判断：能不能上。别写“基本可用”这种话，要么能上要么不能上。
