# DRILL-2026-10-19 故障演练记录

演练日期：2026-10-19
项目：docseek
版本：v0.18.1（C++17）
演练人：编排 agent（真实执行）
文档状态：实测记录

## 演练目标

验证 docseek 在 SQLite WAL 模式下的以下能力：

1. 建库与索引是否正常。
2. 在线备份是否可用。
3. serve 模式搜索接口是否正常。
4. 进程被强杀（kill -9）后 WAL 数据是否丢失。
5. 数据库文件被误删后能否从备份恢复。
6. 恢复后数据是否与备份时一致。
7. 恢复无效备份文件时是否安全拒绝，且不影响当前库。

## 环境

- 操作系统：Linux VM
- docseek 版本：v0.18.1，C++17 构建
- 数据库：SQLite，WAL 模式
- 演练库文件：drill.db
- 备份文件：drill-backup.db
- 语料：corpus 目录下 3 个 markdown 文件，共 297 字节
- serve 端口：18321

### 步骤 3：启动服务并查询

命令：

```

```

另开终端执行：

```
curl "http://127.0.0.1:18321/api/search?q=弹力带"
```

返回结果：hits 中包含 doc1.md，snippet 正常。

结果：通过。

### 步骤 4：强杀 serve 进程并重启验证

先执行：

```
pkill -9 -f "docseek --db drill.db serve"
```

第一次执行时，pkill 的匹配串把自己所在的 shell 命令行也匹配上了，导致当前会话被一并杀掉。改用括号技巧规避：

```
pkill -9 -f "docseek --db drill.db serv[e]"
```

这次成功只杀掉了 serve 进程。

重启 serve 后执行 stats，输出仍为 3 篇文档。执行 search "弹力带"，正常返回 2 条结果。WAL 未丢失数据。

结果：通过。但操作过程暴露了 pkill -f 的自杀风险，详见“发现的问题与改进”。

### 步骤 5：模拟删库

命令：

```

```

实际执行时，drill.db-shm 和 drill.db-wal 已被 SQLite 打开时自动清理，rm 对这两个文件报 No such file。这属于正常现象，drill.db 本身被成功删除。

结果：通过。

```

```

输出：


随后 stats 再次确认：

结果：通过。

## 发现的问题与改进

### 问题 1：pkill -f 匹配串自杀

第 4 步第一次执行：

```
pkill -9 -f "docseek --db drill.db serve"
```

这条命令的匹配串会匹配到当前 shell 自己的命令行，因为当前 shell 的命令行里也含有这串文本。结果 pkill 把自己所在的会话也杀了，后续命令没有继续执行。

规避方式：把匹配串里某个字符改成字符类，让命令行文本不再逐字匹配自己，例如：

```
pkill -9 -f "docseek --db drill.db serv[e]"
```

这样 pkill 的命令行里出现的是 `serv[e]`，而目标进程命令行里是 `serve`，正则能匹配目标，但不会匹配 pkill 自己。

运维注意事项：

- 用 pkill -f 之前，先跑一次 `pgrep -af <pattern>` 看清楚会命中哪些进程。
- 匹配串尽量写全，不要用太短的词，避免误伤。
- 需要长期在脚本里用时，优先用 pidfile 或 `pgrep` 取 PID 再 `kill`，不要直接 `pkill -f`。
- 本次是交互式终端，被误杀只影响当前会话；如果是在远程 SSH 或自动化流水线里，误杀可能直接中断整个任务。

### 问题 2：rm WAL/SHM 文件报 No such file

第 5 步里，`rm drill.db drill.db-shm drill.db-wal` 对后两个文件报 No such file。原因是 SQLite 在连接关闭或 checkpoint 后会自动清理 -shm 和 -wal。这不是故障，是正常行为。演练记录里保留这条，是为了避免下次有人看到报错就以为删库步骤失败了。

改进建议：删库脚本里对 -shm/-wal 用 `rm -f`，不要因为这两个文件不存在就让脚本退出非零。
