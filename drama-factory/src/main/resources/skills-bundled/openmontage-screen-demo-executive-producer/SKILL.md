# 总制片人 — 屏幕演示流水线

## 适用时机

当你要产出一条屏幕演示视频时，你就是总制片人（EP）。你的职责是按顺序把每个阶段的导演拉起来、审阅其产物，然后决定放行还是打回重做。

本流水线**没有前期筹备阶段**（不做调研、不做提案），因为源素材已经存在。EP 的价值在于补上跨阶段的质量闸门，把文字可读性、声音清晰度和节奏问题尽早拦下来，避免拖到昂贵的合成环节才发现。

## 为什么需要这一层

屏幕演示视频有一批并行执行时容易被忽略的典型故障：

- 录屏里的界面文字经过裁切与缩放后变得无法辨认
- 规划阶段看着合理的放大裁切区域，实拍中把关键控件挡掉了
- 键盘敲击声与环境底噪一路留到成片
- 加载画面、打字停顿等无效时间不加速就没法看
- 标注浮层遮住了它本要强调的界面元素
- 字幕位置与画面内容打架

EP 要在尽可能早的节点把这些都抓出来。

## 执行协议

### 阶段 0：初始化

1. 载入流水线清单（`screen-demo.yaml`）
2. 载入手册（用户指定或默认）
3. 设定预算（来自配置或用户输入；默认 1 美元，屏幕演示通常成本很低）
4. 初始化 EP_STATE

### 阶段 1：串行执行各阶段

按顺序推进：`idea → script → scene_plan → assets → edit → compose → publish`

```
EXECUTE_STAGE(stage_name):

  1. 准备
     - 载入该阶段的导演技能
     - 把 EP_STATE 作为上下文注入
     - 注入此前返修留下的 EP 反馈

  2. 拉起导演
     - 导演执行完整流程
     - 导演产出产物

  3. 审阅
     - schema 校验
     - 检查流水线清单里的 review_focus
     - 检查流水线清单里的 success_criteria
     - 执行 EP 专属跨阶段检查（见下文）

  4. 闸门决策
     通过 → 存储产物、更新追踪、继续
     返修 → 返修计数加一，带反馈重跑（最多 3 次）
     打回某阶段 → 从该阶段起重跑（每对阶段最多 1 次）
```

### 阶段 2：终检

```
FINAL_QA:
  1. 探测输出视频：
     - 时长：与演示内容是否相称？
     - 分辨率：是否达到目标？
     - 音频：旁白是否清晰？键盘噪声是否已清除？
     - 文件：容器是否合法、体积是否合理？

  2. 可读性检查（屏幕演示命门）：
     - 在输出分辨率下界面文字是否可读？
     - 放大裁切区域是否确实展示了目标控件？
     - 标注浮层是否没挡住关键内容？

  3. 节奏检查：
     - 加载与打字停顿是否已加速或剪掉？
     - 演示推进是否符合逻辑？
     - 工作流步骤之间的转场是否顺滑？

  4. 字幕检查：
     - 字幕是否与画面内容重叠？
     - 字幕时间轴是否贴合语音？

  5. 预算结算：
     - 实际总花费对比预算
     - 记录各阶段成本明细

  6. 决策：
     全部通过 → 批准发布
     可读性问题 → 打回合成（重渲）或打回场景（重规划裁切）
     音频问题 → 打回合成（重混）
     节奏问题 → 打回剪辑（重新配时）
```

## EP 专属跨阶段检查

### IDEA 阶段之后：
```
检查：源素材评估
  - 源素材是否被引用且可访问？
  - 目标平台与时长是否现实？
  - 标注/放大需求是否已识别？
  - 若无源素材：停止 —— 本流水线必须有源素材
```

### SCRIPT 阶段之后：
```
检查：转写质量
  - 若源素材带旁白：转写是否准确并带时间戳？
  - 关键界面操作是否标注了时间戳？
  - 工作流步骤切分是否清晰？
  - 为素材阶段标记是否存在键盘噪声

检查：时长估算
  - 预估输出时长与内容是否匹配？
  - 若演示超过 5 分钟：建议裁剪或加速
```

### SCENE_PLAN 阶段之后：
```
检查：放大裁切可行性
  - 每个裁切区域是否捕获了目标控件？
  - 裁切区域是否至少为源分辨率的 50%？（避免过度放大的像素化）
  - 把 zoom_regions 存入 EP_STATE，供合成阶段核对

检查：标注摆放
  - 标注浮层（箭头、高亮、遮罩）是否避开了它引用的控件？
  - 标注是否克制？（同时最多 2-3 个）

检查：节奏规划
  - 无效时间段落（加载、打字）是否已标记加速或剪掉？
  - 速度变化是否平滑（不是生硬跳变）？
```

### ASSETS 阶段之后：
```
检查：字幕定位
  - 字幕是否避开了关键画面内容？
  - 字幕字体在画面背景上是否可读？

检查：音频质量
  - 若使用了 audio_enhance：键盘噪声是否降低？
  - 若生成了 TTS：旁白时序是否与画面动作对齐？

检查：预算闸门
  - 若 budget_spent > budget_total * 0.9 且仍有阶段未跑：
      告警并调整剩余阶段
```

### EDIT 阶段之后：
```
检查：时间轴完整性
  - 全部剪辑决策都引用了合法的源文件与素材
  - 若加了背景音乐，是否配置了音频闪避
  - 速度调整是否平滑（渐变而非跳变）

检查：无效时间处理
  - 加载画面与打字停顿是否被剪掉或加速
  - 总无效时间低于输出时长的 10%
```

### COMPOSE 阶段之后：
```
检查：输出校验
  - ffprobe：时长、分辨率、编码、音频通道
  - 输出分辨率下文字是否可读
  - 音频清晰度 —— 旁白全程可听懂

检查：画面锐度（屏幕演示命门）
  - 录制中的界面文字必须可读
  - 若裁切导致像素化：标记需重做场景规划
  - 抗锯齿文字必须能在压缩后存活
```

## 反馈消息模板

### 给脚本导演：
```
EP 反馈 — 脚本需返修
原因：{reason}
具体问题：{转写准确性 / 切分 / 时序}
保留：{哪些做得好}
修改：{具体要改什么}
```

### 给场景导演：
```
EP 反馈 — 场景规划需返修
原因：{reason}
涉及场景：{scene_ids}
约束：{裁切可行性 / 标注摆放 / 节奏}
源分辨率：{W}x{H} — 最小裁切：{W/2}x{H/2}
```

### 给合成导演：
```
EP 反馈 — 需重渲
原因：{reason}
具体问题：{可读性 / 音频 / 节奏}
期望：{输出应该长什么样、听上去如何}
实际：{产出的结果}
```

## 质量闸门汇总

| 闸门 | 所在阶段之后 | 检查内容 | 失败动作 |
|------|-------------|---------|---------|
| G1 | idea | 源素材评估、可行性 | 返修 idea |
| G2 | script | 转写准确性、时长估算 | 返修 script |
| G3 | scene_plan | 裁切可行性、标注摆放、节奏规划 | 返修 scene_plan |
| G4 | assets | 字幕定位、音频质量、预算 | 返修 assets |
| G5 | edit | 时间轴完整性、无效时间处理 | 返修 edit |
| G6 | compose | 输出探测、画面锐度、音频清晰度 | 返修 compose 或打回上游 |
| G7 | publish | 元数据、章节、导出打包 | 返修 publish |
| FINAL | 全部 | 可读性、节奏、字幕、音频 | 打回指定阶段 |

## 执行上限

| 上限 | 取值 | 理由 |
|------|------|------|
| 单阶段最大返修次数 | 3 | 防止完美主义死循环 |
| 单对阶段最大打回次数 | 1 | 防止来回踢皮球 |
| 总打回次数上限 | 3 | 限制总返工量 |
| 总预算上限 | 可配置（默认 1 美元） | 花费硬停 |
| 总墙钟时间上限 | 10 分钟 | 屏幕演示比生成类流水线简单 |

## 常见坑

- **忽视文字可读性**：屏幕演示第一号问题。裁切后务必确认界面文字仍可读。
- **裁切过度**：极端放大会像素化。最小裁切不低于源分辨率的 50%。
- **留着无效时间**：加载画面与打字停顿必须处理，加速或剪掉。
- **标注堆砌**：同时超过 2-3 个标注会让画面混乱。
- **忽视键盘噪声**：源素材若有键盘声，早期就要标记给音频清理。
