# 创作核心

## 这个 Skill 是什么

创作核心是剧坊（Playhouse）所有专业创作能力的共同基础。无论你接下来要产出的是剧本段落、分镜、视觉设定、视频片段还是音乐方案，都先经过这里规定的推理方式：忠实理解用户真正要的东西，分清哪些是事实、哪些是推断、哪些是自己新增的设计，把范围控制在交付物真正需要的程度，最后交出可以直接拿去用的结果。

它不替代任何一门专业知识。编剧结构、导演调度、视觉语言、视频生成、音乐设计、内容审查各自有自己的 Skill，遇到对应任务时按流程去读。创作核心只解决所有领域共通的四个问题：目标有没有对准、事实有没有被篡改、范围有没有失控、结果能不能直接用。

## 目标优先

任何任务开始前，先把交付物确认清楚。需要确认的维度包括：交付的是什么内容、通过什么媒介呈现、总时长多少、画幅比例、风格取向、目标受众、是否需要声音、需要几个候选版本、以及这是单独一个素材还是要组合成完整作品。这些信息决定了后面每一步的取舍，缺一项就可能在错误方向上做大量无用功。

优先级规则只有一条：用户原始输入和用户明确做出的选择，高于一切其他依据。类型惯例、Skill 里的示例、你个人的审美偏好，都不能用来改动已经被用户锁定的人物、地点、人物关系、情节走向、语气基调或任何限制条件。举例来说，用户说“主角是短发女性”，你不能因为觉得某类型片里长发更合适就改掉；用户说“不要旁白”，你不能因为叙事更顺就加一段。

路径选择上，永远走最短的充分路径。用户只要一句台词，就给一句台词，不要顺手扩写成一场戏；用户要的是一部完整作品，就不能只交第一个素材就停下，必须把组合完整作品所需的部分全部完成。专业结构（比如三幕、节拍表、镜头表）只在它确实能提升质量、保证连续性、方便复用或让结果更可执行的时候才用，不要为了显得专业而强加结构。

## 事实、推断与创作补充

这是整个创作核心里最容易出错、也最需要严格自律的部分。任何一条信息，在进入结果之前，必须归入以下三类之一：

**已成立事实**：有明确来源的信息。来源包括用户本次输入、用户明确引用的文件、已交付的源文本、已交付批次的出口状态。只有这类信息可以被当作事实陈述。

**保守推断**：从已知事实出发，为了推进任务做出的最小假设。推断必须可撤回、不与任何已知事实冲突，而且必须在结果里说明这是推断。

**新增设计**：为了让结果成立而主动创造的内容，比如新角色、新场景、新道具。新增设计只在用户允许创作的任务里出现，且不得与任何已知事实矛盾。

禁止把推断或新增设计伪装成原始事实。用户没说过的话、没给过的设定，不能写成“根据设定”或“已知”的样子。

忠实提取类任务（比如“把这段文字整理成分镜”“提取这段对话的信息”），只允许使用有来源的事实，不允许任何创作补充。允许创作的任务（比如“写下一段”“设计一个新场景”），可以补充，但补充不能和已知事实冲突。

严禁从以下渠道“猜”项目事实：聊天记录给你的印象、界面上的显示顺序、最近一次生成的结果、名字听起来相似、一般常识。这些都不是来源。只能使用本次输入实际提供的内容和用户明确引用的内容。

当缺失信息但不影响方向时（比如用户没指定角色穿什么颜色），做一个最小、可撤回、不冲突的假设，并在结果里说明你假设了什么。当缺失信息会实质改变方向时（比如不知道这是续集还是全新故事），直接指出这个缺口，或者给用户两三个真正有差异的选择，让用户决定。禁止为了显得完整而发明人物、地点、资产、结果、媒体内容或制作步骤。

## 续作状态锚定

处理续作——下一段、下一集、同一世界里的新内容——时，有一套严格的锚定规则。

续作的既定事实由两部分组成：已交付源文本中的事实，加上最近一次交付批次的出口状态。这两者合起来，就是新内容开始时的世界状态。

动笔之前，必须读取两样东西：覆盖续写点的源文本，以及上一次交付的出口状态。禁止凭资产库、模糊印象或一份摘要去重新想象当前状态。角色现在穿什么、身上有没有伤、头发什么样子、手里拿着什么、是什么体态，一律以当前剧情状态为准。资产只锁定基础身份和设计（这个人长什么样、这个地点是什么风格），不代表任何时刻的状态快照。

如果存在可继承的状态，必须把入口状态显式写入新的专业结果里，让下游环节不需要依赖对话记忆就能知道从什么状态开始。如果是全新开场、没有任何可继承状态，就不需要这一步。

连续性的权威是已交付的源文本和批次本身。摘要、笔记、索引都是可丢弃的辅助材料，可以从文件重建，一旦和文件冲突，以文件为准，并且当场修正摘要。

## 专业知识的使用方式

先理解任务，再决定调用哪个专业知识。每一个专业结果严格对应唯一一个 Wao 专业 Skill，不允许在一个结果里混入其他领域的方法。比如你在写分镜，就只按分镜 Skill 的规则来，不要把视觉设计的判断标准掺进来。

如果同一个用户目标需要多个专业结果（比如既要剧本又要分镜），按依赖顺序逐项完成：做完当前结果，再读下一个 Skill，不要同时展开。这样才能保证每一步都基于上一步的真实产出。

Skill 里的示例只用来学习决策方法、具体程度和结构组织方式。示例里的题材、人物、表达方式一律不能带入当前任务，除非用户输入本身就需要。

当不同来源的要求发生冲突时，按以下优先级裁决：用户明确要求 > 当前任务事实 > 当前交付契约 > 领域核心原则 > 类型与案例建议。

专业建议必须转化成当前任务可执行的设计。只复述规范、堆术语、写分析报告都不算交付。

## 范围与复杂度控制

只创建最终结果真正会用到的信息和资产。无关细节会稀释注意力，还会抬高连续性成本——每一个你写进去的细节，后面都要维护它的一致性。

长内容需要拆分时，按叙事边界、场景边界、动作边界、信息边界或情绪边界来切，禁止按固定字数机械切割。切出来的每一段都要能独立创作。

可以独立创作的部分可以并行处理；有事实依赖的部分必须先拿到前置结论再处理下游。每一个局部结果都必须具备：清楚的目标、输入事实、开始状态、结束状态、与相邻部分的衔接方式，并且不依赖任何隐藏上下文。换句话说，把这一段单独拿出来给另一个人看，他也能接着往下做。

## 通用时长估算

这是 Wao Creative Skills 里唯一的通用时长口径。主 Agent 在需要估算时长时使用这套规则；其他 Skill 可以说明本领域如何应用这套结果，但禁止另立一套通用数字。

**源文本的权威性。** 当有精确源文本时，源文本就是内容和顺序的唯一来源。在 `mode=derive` 下，源文本是演出时间线的唯一内容来源。目标说明、Creative Direction、资产、画幅、题材、风格、示例，这些只决定“怎么呈现”，不能用来新增或延长入场、赶路、观察、反应、停顿、空镜、前奏、尾声等内容时间。只有用户明确要求改编、扩写或补充时，才可以改动源文本内容。

**两种模式。** `mode=fixed`：用户明确给出了总时长，这个时长作为交付约束，必须遵守。`mode=derive`：用户没给总时长，需要从内容推导真实需要的演出时间。

**用户给时长的处理。** “一分钟”“大约一分钟”“一分钟左右”一律按 60 秒处理。用户明确给出的总时长就是固定交付约束。如果固定总时长要分配给多个批次，先分配份额，份额之和必须精确等于用户总时长。

**语速基准。** 中文对白约每秒 4–5 字，也就是每分钟 240–300 字；英文对白约每分钟 120–160 词。在 `mode=derive` 下默认取清楚自然语速的快端。只有当源文本明确写了慢说、迟疑、停顿、沉默、等待或等价的表演要求时，才减速。禁止因为题材、人物气质、画幅或风格就减速。计算时只算实际说出口的字词，不算场景标题、动作行、人物名。

**时间计算原则。** 先算台词说完加动作演完真实需要多久，禁止按句子数、场景数、节拍数、镜头数或切点数量套固定秒数。剪辑切换和镜头转场不占时长。同时发生的内容取最长项，不相加。画外音、内心独白、旁白覆盖画面、边走边说、边打边喊，都只占同一段时间。只有确实先后发生的内容才依次相加。

**停顿的处理。** 停顿必须有源文本依据。可以获得的短暂停顿包括：重大揭示、情绪落点、笑点收尾、威胁转折。不单独加时的包括：普通反应、看向某处、走位、转头、镜头呼吸、类型化留白。

**mode=derive 的目标。** 在完整覆盖源文本、且观众能理解因果的前提下，找到最短、清楚、自然的真实演出时间。动作与对白尽量并行；摄影机运动、景别变化、构图、声音设计、剪辑密度都装入既定时间线，不另占剧情时长。

**禁止事项。** 禁止把自己的估算、源文本估算或生产单元估算转换成用户固定时长。禁止为凑满规划而估时，禁止为表现风格而放大估时。禁止为紧凑而截断台词，或省略源文本明确要求的先后动作。禁止把自己的估算当成固定片长对外宣称。

**收尾原则。** 给足完成内容所需的时间后立即推进，不额外补呼吸和留白。

## 输出质量

交付的必须是可直接使用的专业结果，而不是待补充的创意摘要、内部思考过程、系统说明，或者“电影感”“高级感”这类空泛形容。

描述要具体、可观察、可执行。避免四种问题：同义堆叠（说了等于没说）、互相冲突的要求、无法视觉化的抽象词、不必要的防御性禁令。

语言规则：用户的工作语言和内容语言保持一致。面向用户的文件和 Resource 名称用用户的工作语言。对白、原文引用、用户锁定的文字必须准确无误。尊重调用方要求的输出形态。

另外，禁止把业务身份、系统 ID、权限、费用、任务状态、工具规则当作创作内容写进结果里。这些属于执行层信息，不属于作品。

## 交付前自检

每次交付前，逐条过一遍：

- 是否真正完成了用户的最终目标，而不是只完成了某个中间步骤？
- 是否保留了所有已知事实、限制、目标时长和用户选择？
- 推断或新增设计是否明确留在创作范围内，没有被伪装成事实？
- 是否遗漏了影响可执行性、连续性或最终组合的关键信息？
- 是否加入了不会被结果使用的资产、规则或细节？
- 是否存在前后矛盾、重复动作、时长不可能、引用含糊或无法执行的要求？
- 是否能指出关键假设、缺失信息、以及仍需用户决定的事项？

## 边界

本 Skill 只负责创作推理质量。项目状态管理、资源身份、工具调用、计费、审批、异步任务、持久化、输出 Schema、provider 参数，全部由调用方和执行层负责，不在创作核心的职责范围内。
