# 分享读接口限流评估报告

> 注（v1.8，2026-10-17）：本报告评估的是 v1.7 的 token+IP 双维度实现（`MINIOS_SHARE_READ_RPM`/`_BURST`、
> `auth_ops_total{op="share_ratelimited"}`）。v1.8 已重设计为 IP 单维度独立令牌桶，
> 环境变量改为 `MINIOS_SHARE_RPS` / `MINIOS_SHARE_BURST` / `MINIOS_SHARE_RATE_LIMIT_ENABLED`，
> 指标改为 `minios_share_rate_limited_total`，旧变量被设置即启动失败。运维调参以 OPERATIONS.md §10 为准，
> 本报告的压测数据仅保留作历史参考。
## 1. 背景与范围

mini-os 为三条公开分享读路由新增了限流：

- `GET /api/s/:token`
- `GET /api/s/:token/download`
- `GET /api/share/list`

限流采用 token + IP 双维度令牌桶，复用现有 `RateLimiter` 实现，第二维键为 token。默认参数：

- `MINIOS_SHARE_READ_RPM=30`，即 rps = 0.5
- `MINIOS_SHARE_READ_BURST=30`

任一维度超限即返回 429，响应头带 `Retry-After`，响应体为：

```json
{"error":"分享访问过于频繁，请 <secs> 秒后重试","retry_after":<secs>}
```

超限计数写入 `auth_ops_total{op="share_ratelimited"}`。

本文档只使用两组真实压测/实测数据，超出数据范围的推断均显式标注为「推导」。

## 2. 压测方法

### 2.1 脚本原理

`scripts/share-load-test.py` 的流程：

1. 启动本机 release 二进制真服务；
2. 注册账号；
3. 创建文件；
4. 创建分享，拿到 token；
5. 多线程按目标速率打流；
6. 汇总状态码、`retry_after` 分布、成功响应延迟、跨 token 成功率。

### 2.2 环境

- 本机 release 二进制
- 并发：8
- 时长：20 秒
- 参数：`--rpm 30 --burst 30`

### 2.3 数据组 A：持续打流

命令：

```
scripts/share-load-test.py --rpm 30 --burst 30 --duration 20 --concurrency 8
```

结果：

| 指标 | 数值 |
| --- | --- |
| total | 16989 |
| 200 | 40 |
| 429 | 16949 |
| retry_after 1s | 8909 |
| retry_after 2s | 8040 |
| 200 响应 p50 | 5.27ms |
| 200 响应 p99 | 34.98ms |
| other_token_ok_ratio | 0.00 |

说明：同 IP 下第二个 token 的 5 次请求全部 429（`other_token_ok_ratio=0.00`）。这是 IP 桶的期望行为，不是 bug：该 IP 的桶已在前一 token 的打流中被耗尽，第二个 token 仍受同一 IP 桶约束。

### 2.4 数据组 B：手动场景

同一服务，`rpm=30 / burst=30`：

| 场景 | 结果 |
| --- | --- |
| 正常速率 1 req/s × 10 次 | 10/10 返回 200 |
| 连续 burst 40 次 | 25×200 + 15×429 |
| 429 响应头 | `retry-after: 2` |
| 429 响应体 | `{"error":"分享访问过于频繁，请 2 秒后重试","retry_after":2}` |
| 新 IP（X-Forwarded-For: 9.9.9.9）+ 新 token | 200 |
| /metrics | 含 `auth_ops_total{op="share_ratelimited"} 18` |

连续 burst 40 次前，正常速率测试已消耗约 5 个 token，桶内剩余 25，因此得到 25×200 + 15×429，与数学吻合。

## 3. 数据解读

### 3.1 为什么 16989 次里只有 40 次 200

桶初始容量 30，补充速率 rps = 0.5，持续 20 秒。

- 初始可放行：30
- 20 秒内补充：0.5 × 20 = 10
- 合计约 40

与实测 200 = 40 完全吻合。其余 16949 次在桶空后立即被拒，因此 429 占绝大多数。

### 3.2 retry_after 为什么是 1~2s

rps = 0.5，补 1 个 token 需要 2 秒。请求到达时距上次补充的间隔不同，因此等待时间落在 1s 或 2s。实测分布 `{1s: 8909, 2s: 8040}`，两者接近对半，符合连续打流下到达时刻均匀分布的预期（推导）。

### 3.3 限流器开销

200 响应 p50 = 5.27ms，p99 = 34.98ms。这两项是成功请求的端到端延迟，限流判定在请求入口完成，量级远小于业务处理，因此限流器本身开销可忽略（推导）。

## 4. 正常用户影响分析

### 4.1 正常浏览（≤1 次/秒）

实测 1 req/s × 10 次全部 200。个人云桌面场景下，人工浏览分享页的请求频率远低于 1 次/秒，因此默认参数对正常用户无影响。

### 4.2 单链接被刷（同一 token 高频）

token 桶按分享链接聚合，30/分钟封顶，超出即 429。这是设计目标：防止单个热链被刷爆，保护后端与带宽。

### 4.3 单 IP 轮询多 token

IP 桶按客户端 IP 聚合，30/分钟封顶，超出即 429。这用于防止单 IP 枚举爬取。实测 `other_token_ok_ratio=0.00` 正是该机制生效的表现，属于期望行为。

需要注意的副作用：NAT、公司出口 IP、运营商 CGNAT 下，多用户共享同一个 IP 桶，会被误伤。缓解建议：

- 调大 `MINIOS_SHARE_READ_BURST`，给共享出口留余量；
- 在可信反代后按 `X-Forwarded-For` 透传真实客户端 IP，使 IP 桶按真实用户聚合，而不是按出口 IP 聚合。

### 4.4 爆款分享链接（多 IP 正常访问同一 token）

token 桶是跨 IP 聚合的，与访问者 IP 无关。一个链接被大量不同 IP 的正常用户访问时，30/分钟后所有人都 429。

这是当前设计的 trade-off：安全性优先于热点链接的可用性。调参建议：

- 提高 `MINIOS_SHARE_READ_RPM`，为热链留出更高配额；
- 未来可考虑分级配额（例如按分享创建者、分享类型或白名单区分），但当前版本未实现，属于后续工作。

## 5. 阈值推荐

默认 `MINIOS_SHARE_READ_RPM=30`、`MINIOS_SHARE_READ_BURST=30` 保留。理由：

- 个人云桌面场景下，正常分享访问远低于 30/分钟；
- 暴力枚举成本被抬高约 2 个数量级（推导：从无限制到 30/分钟）。

三档参考：

| 档位 | RPM | BURST | 适用场景 |
| --- | --- | --- | --- |
| 保守 | 10 | 10 | 高敏感分享、对外暴露面大、优先防爬 |
| 默认 | 30 | 30 | 个人云桌面常规使用 |
| 开放 | 120 | 120 | 内部可信网络、热点分享、共享出口 IP 较多 |

调参只改两个环境变量，不需要改代码；生效方式取决于进程启动方式，通常重启进程即可。

## 6. 已知限制

- 单进程内存桶：多实例之间不共享配额，各自独立计数；进程重启后桶清零。
- 与登录限流使用同一套 `RateLimiter` 实现，因此共享上述限制。
- IP 桶依赖客户端 IP 的正确获取；未正确透传 `X-Forwarded-For` 时，反代后的所有请求会被聚合成同一个 IP。
- token 桶跨 IP 聚合，爆款链接在默认参数下会出现全员 429，见 4.4。
