# 房间类型-运维手册

这篇写给值班的人看。上线之后房间里可能出什么事，怎么查，怎么改，都在这。

## 一、两套房间，别搞混

房间分两种，字段是 `type`，存在 `rooms` 表里，取值只有 `'workroom'` 和 `'playroom'`。建房间的时候不写就按 `workroom` 走。列定义是 `type TEXT NOT NULL DEFAULT 'workroom'`，所以老数据升级完自动都是 `workroom`，不用手工刷。

工作房给干活用，玩房给游戏用。别在玩房里发任务，发了会被拒。

## 二、人数上限和环境变量

两个环境变量管人数：

- `ROOM_MAX_MEMBERS_WORKROOM`，默认 50
- `ROOM_MAX_MEMBERS_PLAYROOM`，默认 200

这俩值在服务启动时读一次。要是填了 `abc`、`0`、`-1` 这种非法值，进程直接起不来，这是故意的，别想着绕过。日志里会写明是哪个变量、填了什么值，照着改就行。

改完要重启才生效，热改不支持。

还有一个 `GAME_BROADCAST_THROTTLE_MS`，默认 500，单位毫秒。它管游戏状态广播的频率，同样启动时校验，非法值一样 fail-fast。

## 三、改房间类型

接口：

```
POST /api/rooms/:id/type
Body: {"type": "playroom"}
```

`:id` 换成房间 ID，`type` 只能填 `workroom` 或 `playroom`，填别的会报错。

注意：从 `playroom` 改回 `workroom` 之后，房间里已有的游戏会话不会自动清掉，`game_sessions` 表里的记录还在。如果不想留，得手工处理，现在没有批量清理接口。

## 四、房间统计

接口：

```
GET /api/rooms/:id/stats
```

返回这个房间的聚合数据，用来快速看房间健不健康。值班时先打这个接口，再决定往哪查。

## 五、设置人格角色

接口：

```
POST /api/rooms/:id/persona
Body: {"persona_id": "...", "role": "..."}
```

对应的存储列是 `room_members.persona_role`，`TEXT` 类型，允许为空。一个成员在房间里的角色就记在这。

`persona_id` 填的是人格标识，`role` 是这个人在房间里扮演什么。两个字段都得是真实存在的值，乱填会返回错误。

## 六、ROOM_TYPE_FORBIDDEN 怎么处理

这是最常见的报错，遇到别慌。

触发条件：在 `playroom` 里发了 `intent=task` 的消息。返回 HTTP 400，body 是：

```json
{"error":"ROOM_TYPE_FORBIDDEN"}
```

排查步骤：

1. 先确认房间 `type` 是不是 `playroom`，用 `GET /api/rooms/:id/stats` 或直接查库。
2. 确认客户端发的是不是 `intent=task`。
3. 如果是客户端发错了，让客户端改成正确 intent，或者把房间改成 `workroom`。

这不是服务端 bug，是契约里的硬性拦截。别去改判断逻辑。

## 七、游戏会话表

游戏状态存在 `game_sessions` 表：

```
id TEXT PRIMARY KEY
room_id TEXT NOT NULL
game TEXT NOT NULL
phase TEXT NOT NULL DEFAULT 'lobby'
state TEXT NOT NULL DEFAULT '{}'
updated_at INTEGER NOT NULL
```

`state` 是 JSON 字符串，默认空对象。`phase` 默认是 `lobby`。

查某个房间的游戏：

```sql
SELECT * FROM game_sessions WHERE room_id = ?;
```

`updated_at` 是毫秒时间戳，用来判断会话是不是卡住了。要是 `updated_at` 很久没动，先看进程活着没，再看有没有报错。

## 八、WebSocket 帧

新增两种帧类型：`game_action` 和 `game_state`。

payload 形状：

```
{
  "game": string,
  "seat": string,
  "action": unknown,
  "state": unknown,
  "state_hash": string
}
```

`game` 必填，其他看情况。`game_state` 帧里一般带 `state` 和 `state_hash`，`game_action` 帧里一般带 `seat` 和 `action`。

`state_hash` 用来对状态做校验，客户端可以拿它比对本地状态，不一致就重新拉。

## 九、兼容和协议版本

协议版本升到 v1.3。老客户端遇到不认识的帧类型会直接忽略，不会崩。所以新帧发出去，老客户端最多是收不到游戏内容，不会报错。反过来也一样，新服务端能正常处理老客户端。

如果值班时发现某个客户端一直在重连，先确认它是不是太老，读不了 `game_state`。

## 十、上线前检查清单

1. 三个环境变量都确认过，没填非法值。
2. 数据库迁移跑完，`rooms.type`、`room_members.persona_role`、`game_sessions` 都在。
3. 随便建一个 `playroom`，发个 `intent=task`，确认收到 `ROOM_TYPE_FORBIDDEN`。
4. 打一次 `GET /api/rooms/:id/stats`，返回正常。
5. 用 `POST /api/rooms/:id/persona` 设一次角色，查库确认 `persona_role` 写进去了。
6. 建一个游戏会话，确认 `game_sessions` 有记录且 `updated_at` 在动。
