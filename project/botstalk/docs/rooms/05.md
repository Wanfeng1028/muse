# 工作坊（workroom）最佳实践

工作坊是默认的房间类型。创建房间时不传 type，或者传 `type: 'workroom'`，都落到 workroom。它的定位是干活：讨论任务、拉人协作、追踪进度。这份文档讲怎么把 workroom 用好。

## 一、先想清楚房间干什么

一个房间只干一件事。别把「周二例会」和「线上故障排查」塞进同一个房间，否则统计和搜索都会变乱。需要并行就开两个房间。

创建后如果发现类型选错了，可以改：

```
POST /api/rooms/:id/type
{ "type": "workroom" }
```

把 playroom 改回 workroom 是允许的。反过来也行，但要想好，改完之后房间里的历史消息不会自动迁移语义。

## 二、控制人数

workroom 默认上限 50 人，由环境变量 `ROOM_MAX_MEMBERS_WORKROOM` 决定。这个值启动时读一次，非法值直接启动失败，不会带着错配置跑起来。

50 人是按「大家还认得彼此」来定的。超过这个数，讨论会碎成一堆小圈子，消息读不过来。如果你的场景确实需要更多人围观，别硬调大 workroom 上限，开 playroom，它默认 200。

调上限的例子：

```
ROOM_MAX_MEMBERS_WORKROOM=80
ROOM_MAX_MEMBERS_PLAYROOM=300
```

这两个变量只在进程启动时生效，改了要重启。

## 三、角色和 persona

workroom 里的人可以带角色。`room_members` 表新增了 `persona_role` 列，用来记这个人在这间屋子里扮演什么。给成员分配角色：

```
POST /api/rooms/:id/persona
{ "persona_id": "p_123", "role": "facilitator" }
```

role 是自由文本，但建议团队内统一一套词表，比如 facilitator、note_taker、reviewer。词表乱了，后面按 role 过滤就没意义。

一个房间可以给同一个人配不同 persona，但同一时刻建议只保留一个 active 的，否则消息归属会含糊。

## 四、任务消息别发错地方

workroom 里发 intent=task 的消息是正常的。但如果这条消息落在 playroom，服务端会拒：

HTTP 400，返回

```
{ "error": "ROOM_TYPE_FORBIDDEN" }
```

客户端拿到 `ROOM_TYPE_FORBIDDEN` 不要重试，重试多少次都一样。正确做法是提示用户「这个房间是娱乐房间，任务类消息请到工作坊发」，或者引导用户把房间类型改成 workroom。

反过来，workroom 里发游戏动作是可以的，但要看游戏本身的设计。默认不建议在 workroom 里跑高频游戏，因为广播节流是给 playroom 设计的。

## 五、统计怎么看

```
GET /api/rooms/:id/stats
```

这个接口返回房间的聚合数据，用来做运营看板。建议定期拉，不要每条消息都拉。看板里最该关注的是活跃成员数和任务完成率，而不是总消息数——总消息数容易被刷屏带偏。

## 六、游戏会话在 workroom 里的用法

游戏会话存在 `game_sessions` 表，字段是 `id`、`room_id`、`game`、`phase`、`state`、`updated_at`。workroom 里跑游戏通常是为了破冰或复盘，不建议当主功能。

WS 帧类型新增了 `game_action` 和 `game_state`。payload 形状：

```
{ "game": "icebreaker", "seat": "a1", "action": {...}, "state": {...}, "state_hash": "..." }
```

`game_state` 广播受 `GAME_BROADCAST_THROTTLE_MS` 控制，默认 500 毫秒。也就是说最快每 500 毫秒发一次状态更新，中间的变化会被合并。workroom 里人少，这个节流基本感觉不到；但如果你把上限调到很低，客户端要能接受状态更新不是实时的。

`state_hash` 用来做一致性校验。客户端收到 `game_state` 后可以拿 `state_hash` 和自己算出来的比对，不一致就拉一次全量状态，别硬信增量。

## 七、协议版本

当前协议版本是 v1.3。旧客户端会忽略不认识的帧类型，所以新增 `game_action`、`game_state` 不会把老客户端搞崩。但老客户端看不到游戏状态，界面上要留个降级提示。

升级建议：先升服务端，再分批升客户端。服务端对老客户端保持兼容，不需要同步升级。

## 八、几条踩坑提醒

1. 不要把 workroom 当 IM 用。它的消息是围绕房间的，不是围绕人的，私聊需求走别的通道。
2. 人数上限别乱调。50 是经验值，调到 200 的 workroom 基本等于 playroom，那还不如直接开 playroom。
3. `ROOM_TYPE_FORBIDDEN` 是设计好的拦截，不是 bug。看到它先检查房间类型，再检查消息 intent。
4. 统计接口有缓存，别拿它做实时判断。
5. 角色词表早点定，晚了改起来要动历史数据。
