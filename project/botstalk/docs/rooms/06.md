# 娱乐厅运营指南

这篇文档写给开娱乐厅（playroom）的人看。工作间（workroom）是大家干活的地方，娱乐厅是大家放松的地方，两边规则不一样，别搞混。下面按“怎么建、怎么管、怎么玩、出问题怎么办”四块讲。

## 一、建一个娱乐厅

建房间的接口跟以前一样，只是多带一个 type 字段。房间创建时指定 type，不写就是默认的 workroom：

```
POST /api/rooms
{ "name": "周五狼人杀", "type": "playroom" }
```

RoomType 只有两个值：`workroom` 和 `playroom`。建好之后也能改，用这个接口：

```
POST /api/rooms/:id/type
{ "type": "playroom" }
```

改完 rooms 表里那行的 type 列就变成 `playroom`。注意 type 列定义是 `TEXT NOT NULL DEFAULT 'workroom'`，不会出现空值。

## 二、人数上限和环境变量

娱乐厅默认最多 200 人，工作间默认最多 50 人。这两个数能用环境变量改：

- `ROOM_MAX_MEMBERS_WORKROOM`，默认 50
- `ROOM_MAX_MEMBERS_PLAYROOM`，默认 200
- `GAME_BROADCAST_THROTTLE_MS`，默认 500

填了非法值（比如负数、空字符串、非数字），服务启动时直接挂掉，不会带着坏配置跑。改完记得重启，配置只在启动时读一次。

`GAME_BROADCAST_THROTTLE_MS` 管的是游戏状态广播的节流，默认 500 毫秒。娱乐厅人多，动作频繁，如果发现消息刷得太快，可以把它调大，比如 1000；但别调太小，太小会淹掉客户端。

## 三、游戏怎么跑

娱乐厅的游戏状态存在 `game_sessions` 表里，表结构是：

```
id TEXT PRIMARY KEY
room_id TEXT NOT NULL
game TEXT NOT NULL
phase TEXT NOT NULL DEFAULT 'lobby'
state TEXT NOT NULL DEFAULT '{}'
updated_at INTEGER NOT NULL
```

- `game` 是游戏名，比如 `werewolf`
- `phase` 是阶段，刚开房是 `lobby`，开局后由游戏逻辑自己改
- `state` 是 JSON 字符串，存整局的状态
- `updated_at` 是毫秒时间戳，每次更新都要写

客户端和服务端之间通过 WS 通信，新增两种帧类型：`game_action` 和 `game_state`。payload 形状是：

```
{ "game": "werewolf", "seat": "3", "action": {}, "state": {}, "state_hash": "abc123" }
```

- `game` 必填，其余字段按需
- `game_action` 是客户端发上来的操作，比如投票、发言
- `game_state` 是服务端广播出去的状态，客户端拿去渲染
- `state_hash` 用来做一致性校验，客户端可以拿它跟自己算的对一下

协议版本升到 v1.3。旧客户端收到不认识的帧类型会直接忽略，不影响它们继续用，所以升级是平滑的。

## 四、娱乐厅里的任务消息会被拒

娱乐厅是玩的，不是干活的。如果有人往 playroom 里发 `intent=task` 的消息，服务端直接拒，返回：

```
HTTP 400
{ "error": "ROOM_TYPE_FORBIDDEN" }
```

错误码就是 `ROOM_TYPE_FORBIDDEN`，一个字符都不能改。写客户端的时候要专门处理这个码，别当成普通 400 吞掉，不然用户会一脸懵。

## 五、给成员挂 persona

娱乐厅里的角色跟工作间不一样，用 persona 来标。给某个成员设 persona 用：

```
POST /api/rooms/:id/persona
{ "persona_id": "p_123", "role": "seer" }
```

`role` 会写进 room_members 表的 `persona_role` 列。这一列是新加的，旧数据是 NULL，读到 NULL 就当没设，别报错。

## 六、看数据

想知道一个娱乐厅现在什么情况，用：

```
GET /api/rooms/:id/stats
```

返回人数、游戏局数之类的统计。具体字段按服务端实际返回为准，这里不列死，免得跟实现脱节。

## 七、出问题怎么查

按这个顺序排查：

1. 房间 type 对不对，用 `GET /api/rooms/:id/stats` 看一眼
2. 人数是不是撞上限了，对上环境变量
3. 游戏卡住不动，看 `game_sessions` 里那行的 `phase` 和 `updated_at`，`updated_at` 很久没变就是没在跑
4. 客户端收不到状态，先确认 `GAME_BROADCAST_THROTTLE_MS` 没被调得太大
5. 出现 `ROOM_TYPE_FORBIDDEN`，说明有人在 playroom 里发任务消息，要么改客户端，要么把这房间改成 workroom

## 八、几条运营上的实在话

- 娱乐厅别拿来做正经事，任务消息会被拒，硬塞只会让用户觉得卡
- 人数上限按实际机器扛得住来调，200 是默认，不是保证
- 游戏状态广播节流别关，关掉之后人多的时候消息量会炸
- 改完环境变量一定重启，配置不热更新
- 旧客户端不用强制升级，协议升到 v1.3 是兼容的，不认识的帧它们会忽略
