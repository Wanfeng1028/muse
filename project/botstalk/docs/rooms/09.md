# 房间类型和错误码表

这份文档说清楚一件事：房间分两种类型，不同类型的房间能干什么、不能干什么，以及越界时服务端会回什么错误。前端拿到错误码之后应该怎么提示用户，也一并写在这里。

## 房间类型是什么

房间类型由 `RoomType` 决定，只有两个值：`workroom` 和 `playroom`。创建房间的时候可以指定 `type`，不传就按 `workroom` 算。

- `workroom`：干活用的房间。适合讨论任务、对齐进度、走正常聊天流程。
- `playroom`：娱乐用的房间。适合玩小游戏、开一局、跑 game_session 那一套。

两种房间的成员上限不一样，由环境变量控制：

- `ROOM_MAX_MEMBERS_WORKROOM`，默认 50
- `ROOM_MAX_MEMBERS_PLAYROOM`，默认 200

如果这两个变量被设成非法值（比如负数、空串、非数字），服务会在启动时直接失败退出，不会带着坏配置跑起来。部署的时候注意别把它们写错。

## 怎么改房间类型

改类型走这个接口：

```
POST /api/rooms/:id/type
```

请求体是 `{type}`，`type` 只能是 `workroom` 或 `playroom`。改完之后房间按新类型的行为走。

## 房间类型越界会怎样

最典型的一种越界：在 `playroom` 里发了一条 `intent=task` 的消息。游戏房里不应该掺任务消息，服务端会拒绝。

拒绝时返回 HTTP 400，响应体是 JSON：

```json
{ "error": "ROOM_TYPE_FORBIDDEN" }
```

前端拿到这个错误码，提示文案建议写“这个房间是娱乐房，发不了任务消息，换个房间试试”。别直接弹英文码给用户看。

`ROOM_TYPE_FORBIDDEN` 是当前唯一的房间类型错误码。后面如果加了新的类型限制，会往这张表里补，不会复用这个码表达别的意思。

## 房间成员和角色

`rooms` 表新增了 `type` 列，类型是 `TEXT NOT NULL DEFAULT 'workroom'`。也就是说老数据迁移过来默认都是工作房。

`room_members` 表新增了 `persona_role TEXT` 列，用来记录成员在这个房间里挂的人设角色。设置角色走这个接口：

```
POST /api/rooms/:id/persona
```

请求体是 `{persona_id, role}`。`persona_id` 指人设，`role` 是这个人在房间里扮演什么。同一个 `persona_id` 在同一个房间里的 `role` 由业务决定，服务端只存不解释。

## 房间统计

想拿房间的统计信息：

```
GET /api/rooms/:id/stats
```

返回房间当前的成员数、消息数这类计数。具体字段以接口实际返回为准，前端别硬编码不存在的字段。

## 游戏会话和帧类型

娱乐房跑游戏用 `game_sessions` 表：

```
id TEXT PRIMARY KEY,
room_id TEXT NOT NULL,
game TEXT NOT NULL,
phase TEXT NOT NULL DEFAULT 'lobby',
state TEXT NOT NULL DEFAULT '{}',
updated_at INTEGER NOT NULL
```

`phase` 表示当前处在哪个阶段，`lobby` 是默认的等待开局。`state` 存游戏状态，默认空对象 `{}`，`updated_at` 是毫秒时间戳。

WebSocket 那边新增了两种帧类型：`game_action` 和 `game_state`。payload 形状是：

```
{ game: string, seat?: string, action?: unknown, state?: unknown, state_hash?: string }
```

`game_action` 是客户端发动作，`game_state` 是服务端推状态。`state_hash` 用来校验状态有没有对得上，避免乱序或者重复。

游戏广播有节流，由 `GAME_BROADCAST_THROTTLE_MS` 控制，默认 500 毫秒。也就是说再密集的状态变化，最多每 500 毫秒推一次，防止刷屏。这个变量设成非法值同样会在启动时 fail-fast。

## 兼容性

旧客户端不认识 `game_action`、`game_state` 这两个帧类型，直接忽略就行，不要因为收到未知帧就断连或者报错。协议版本升到了 v1.3，客户端和服务端握手时按版本协商，老客户端继续用老行为。

## 错误码速查

| 错误码 | HTTP | 触发条件 | 响应体 |
| --- | --- | --- | --- |
| `ROOM_TYPE_FORBIDDEN` | 400 | `playroom` 内收到 `intent=task` 的消息 | `{ "error": "ROOM_TYPE_FORBIDDEN" }` |

这张表就是当前房间类型相关的全部错误码。加新码之前先想清楚是不是真需要新码，能复用语义就复用，别让前端维护一堆长得差不多的分支。

## 前端处理建议

碰到 `ROOM_TYPE_FORBIDDEN`，别重试，重试还是会失败。正确的做法是提示用户换房间，或者把消息改成非任务 intent 再发。如果房间类型是可改的，也可以引导用户先把房间改成 `workroom` 再发任务消息。

启动配置类错误（`ROOM_MAX_MEMBERS_WORKROOM`、`ROOM_MAX_MEMBERS_PLAYROOM`、`GAME_BROADCAST_THROTTLE_MS` 非法）不会走到前端，是部署阶段就挂掉的问题，运维看日志解决。

游戏帧的节流是服务端行为，前端不用自己再压，收到多少推就按多少渲染，`state_hash` 不一致的时候以服务端为准。
