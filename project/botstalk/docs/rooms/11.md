# 房间类型：数据模型

这篇讲房间类型在数据库里到底存了什么。涉及 rooms、room_members、game_sessions 三张表，以及跟类型相关的几个默认值。看完你应该能自己写 SQL 把房间类型、游戏对局状态查出来。

## rooms 表：type 列

rooms 表加了一个新列：

```
type TEXT NOT NULL DEFAULT 'workroom'
```

含义很直接：每个房间有且只有一个类型，取值只能是 `workroom` 或 `playroom`。建房间的时候如果不传类型，就按 `workroom` 算。

为什么默认是 workroom？因为 workroom 是原来的老行为——大家在一个房间里聊事、发任务型消息。playroom 是新的，专门给游戏和娱乐用。默认值选 workroom，老代码不传 type 也能正常跑，不会因为多了个 NOT NULL 列就炸。

NOT NULL 加 DEFAULT 这两个约束是绑在一起的：既有默认值兜底，又保证列里不会有 NULL。查数据的时候不用写 `type IS NULL` 这种分支。

要改一个房间的类型，走 REST：

```
POST /api/rooms/:id/type
```

请求体是 `{type}`。这个接口不是随便谁都能调的，服务端会校验权限和当前房间状态。

## room_members 表：persona_role 列

room_members 表新增了一列：

```
persona_role TEXT
```

注意这列是允许 NULL 的，没有 DEFAULT。意思是：房间成员不一定有人设角色。普通用户进来聊天，这个字段就是空；如果房间里配了 persona，才往这里写角色。

给成员设 persona 和角色走：

```
POST /api/rooms/:id/persona
```

请求体是 `{persona_id, role}`。一个成员在一个房间里对应一个 persona_role，换了就覆盖。

persona_role 和 type 是两码事。type 决定房间整体是什么性质，persona_role 决定某个成员在这个房间里扮演什么。playroom 里可以有带 persona_role 的成员，workroom 里也可以有。

## game_sessions 表

游戏对局单独一张表：

```
game_sessions(
  id TEXT PRIMARY KEY,
  room_id TEXT NOT NULL,
  game TEXT NOT NULL,
  phase TEXT NOT NULL DEFAULT 'lobby',
  state TEXT NOT NULL DEFAULT '{}',
  updated_at INTEGER NOT NULL
)
```

逐列说：

- `id`：一局游戏的唯一标识，主键。
- `room_id`：这局挂在哪个房间下。游戏是房间内的活动，所以必须有 room_id。
- `game`：游戏名字，比如斗地主、你画我猜这类。
- `phase`：对局阶段，默认 `lobby`。开局前是 lobby，进行中、结算各是别的阶段值。阶段由游戏逻辑自己推进。
- `state`：对局状态的序列化内容，默认空对象 `'{}'`。存的是 JSON 字符串，具体结构由各个游戏自己定义，数据库这层不关心里面长什么样。
- `updated_at`：最后一次更新的时间戳，整数。每次对局状态变化都要刷新这个值，方便判断哪局还活着、哪局是陈年旧局。

`state` 存成 TEXT 而不是结构化列，是因为不同游戏的内部状态差太多。硬要拆成公共列，要么列爆炸，要么每个游戏塞一堆用不上的字段。存 JSON 字符串，游戏自己序列化和反序列化，数据库只负责落盘。

## 房间类型和消息的关系

房间类型会影响消息能不能发。playroom 里发 intent 为 task 的消息会被拒，返回：

```
HTTP 400
{"error":"ROOM_TYPE_FORBIDDEN"}
```

错误码就是 `ROOM_TYPE_FORBIDDEN`。这条规则的意思是：playroom 是玩的，不是派活的。任务型消息在 playroom 里没有意义，直接挡掉，省得房间里一半人在玩游戏一半人在派任务，互相干扰。

反过来，workroom 里发普通聊天、发任务都没问题。游戏相关的动作走 WS 帧，不跟消息 intent 混在一起。

## WS 帧和游戏状态

游戏动作和状态通过 WebSocket 传。新增两种帧类型：

```
game_action
game_state
```

payload 形状：

```
{game: string, seat?: string, action?: unknown, state?: unknown, state_hash?: string}
```

- `game`：游戏名，跟 game_sessions.game 对应。
- `seat`：座位，可选。不是所有游戏都分座位。
- `action`：动作内容，可选，具体结构游戏自己定。
- `state`：对局状态，可选。
- `state_hash`：状态哈希，可选，用来对状态做校验，防止两端状态对不上。

广播游戏状态有节流：

```
GAME_BROADCAST_THROTTLE_MS
```

默认 500 毫秒。游戏状态变化很频繁，每次都广播会把连接打满，所以按这个间隔合并广播。

## 房间人数上限

不同房间类型能装的人不一样，用环境变量控制：

```
ROOM_MAX_MEMBERS_WORKROOM
ROOM_MAX_MEMBERS_PLAYROOM
```

workroom 默认 50，playroom 默认 200。playroom 给游戏用，人多点也扛得住；workroom 是聊正事的，人太多反而乱。

这两个值在服务启动时读。如果配了非法值（不是正整数之类），启动直接失败，不会带着坏配置跑起来。宁可起不来，也别起来之后一半房间能进一半进不去。

## 查房间统计

想知道一个房间当前的情况，走：

```
GET /api/rooms/:id/stats
```

这个接口返回房间的统计信息，具体字段按实现来。房间类型、成员数这些基础信息能从这里拿到。

## 兼容性

协议版本升到了 v1.3。老客户端遇到不认识的帧类型直接忽略，不会因为收到 game_action / game_state 就崩。所以服务端可以放心发新帧，老客户端顶多不处理，不影响它原来的功能。

数据库这边，rooms.type 有默认值，room_members.persona_role 允许 NULL，game_sessions 是新表。老数据迁过来不用特意填 type，默认 workroom 就对了。
