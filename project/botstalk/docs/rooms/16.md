# 房间类型-发布检查单

这份检查单是给 BotsTalk 上线房间类型功能前用的。房间类型现在只有两个值：workroom 和 playroom。建房间的时候可以指定 type，不传就按 workroom 算。下面每一条都得过一遍，别跳。

## 一、数据库

1. rooms 表要有 type 列，类型 TEXT，NOT NULL，默认值 'workroom'。老数据升级后读出来应该是 workroom，不能是空。
2. room_members 表要有 persona_role 列，类型 TEXT，可以空着。老成员这列是 NULL，这是对的，不要给它塞默认值。
3. 新表 game_sessions 要建好，字段是：id TEXT PRIMARY KEY，room_id TEXT NOT NULL，game TEXT NOT NULL，phase TEXT NOT NULL DEFAULT 'lobby'，state TEXT NOT NULL DEFAULT '{}'，updated_at INTEGER NOT NULL。一个字段都不能少，类型也不能改。
4. 用 room_id 查 game_sessions 要能走索引，房间多了以后别全表扫。
5. 升级脚本要在已有数据的库上跑一遍，跑完 rooms.type 不能出现 NULL。

## 二、REST 接口

1. POST /api/rooms/:id/type，body 是 {type}。type 只认 workroom 和 playroom，传别的返回 400。
2. GET /api/rooms/:id/stats，返回房间的统计信息。playroom 和 workroom 都要能调。
3. POST /api/rooms/:id/persona，body 是 {persona_id, role}。role 写进 room_members.persona_role。
4. playroom 里如果有人发 intent=task 的消息，接口要拒掉，HTTP 400，返回的 JSON 就是 {error:"ROOM_TYPE_FORBIDDEN"}。字段名别写错，就一个 error 键。
5. 上面几个接口都要检查调用者是不是房间成员，不是成员按原来的权限逻辑处理。

## 三、WebSocket

1. 帧类型新增 game_action 和 game_state 两种。
2. payload 形状是 {game: string, seat?: string, action?: unknown, state?: unknown, state_hash?: string}。game 必须有，其他按需带。
3. game_action 是客户端发上来的动作，服务端处理完广播 game_state 回去。
4. 广播要限速，用 GAME_BROADCAST_THROTTLE_MS 控制，默认 500 毫秒。同一个房间的高频动作别把连接打满。
5. 旧客户端收到不认识的帧类型要能直接忽略，不能报错断开。这条要拿老版本客户端实测一次。
6. 协议版本改成 v1.3，握手时返回的版本号要对。

## 四、环境变量

1. ROOM_MAX_MEMBERS_WORKROOM，默认 50。
2. ROOM_MAX_MEMBERS_PLAYROOM，默认 200。
3. GAME_BROADCAST_THROTTLE_MS，默认 500。
4. 这三个变量如果给了非法值（不是正整数、是负数、是空字符串、是乱码），进程启动时直接失败退出，别带着错值跑起来。日志里要写清楚是哪个变量不合法。
5. 不设这三个变量时，用默认值，行为要和设了默认值一样。

## 五、兼容性

1. 老客户端不传 type 建房间，建出来是 workroom。
2. 老客户端忽略 game_action 和 game_state，连接不断。
3. 新客户端连老服务端会怎样，这个不在本次范围，但要确认服务端升级后老数据能正常读。

## 六、上线前手动过一遍

1. 建一个 workroom，发任务消息，能过。
2. 建一个 playroom，发 intent=task 的消息，返回 {error:"ROOM_TYPE_FORBIDDEN"}。
3. playroom 里发 game_action，看 game_state 有没有广播回来，state_hash 有没有变。
4. 给房间成员设 persona_role，查回来对得上。
5. 把 ROOM_MAX_MEMBERS_WORKROOM 设成 abc，启动服务，看是不是直接退出。
6. 开两个客户端，一个老版本一个新版本，进同一个 playroom，老版本别掉线。
