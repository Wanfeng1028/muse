# V09 评测回归诊断：docseek v0.14.0 → v0.22.0

## 1. 背景与范围

v0.14.0 → v0.22.0 期间新增的结构加成规则包括：

- R1：标题行加成
- R2：块级同现
- R2b：首段兑现
- R3'：行首命中
- R4：主题前缀
- R6'：行首命中 + 数字
- R7：单 token 时间序数结构

这些规则累计修复 112 个评测对，同时引入 27 个真回归对（基线通过 → 当前失败）。其中跨主题漂移 10 对优先处理。

诊断工具：

- `search --explain`：观察 `base_bm25` / `title_bonus` / `phrase_bonus` / `structural_bonus` 四分量
- `locate --json`：观察 `keywords` / `matched_terms`

---

## 2. 27 个回归对成因分类

从症状看，27 个回归对主要落在两条链路：

1. **search 型**：结构加成翻转了原本正确的 BM25 排序。
2. **locate 型**：passage 排序缺少词特异性权重，且查询噪音词干扰匹配。

### 2.1 search 型：结构加成翻转 BM25

在 10 个跨主题漂移对中，已有 3 对完成 `search --explain` 四分量诊断，根因一致：

| 评测对 | 查询 | structuralBonus | expected 文档 base_bm25 领先 |
|---|---|---:|---:|
| v09-t050-q08 | 肩膀疼 | 3.5 | 1.29 |
| v09-t064-q08 | 训练频率 | 1.5 | 0.905 |
| v09-t085-q03 | 忘词 | 5.0 | 1.248 |

三对的共同模式是：**expected 文档在 `base_bm25` 上本来领先，但 `structural_bonus` 把另一篇结构特征更强的文档推到前面**，导致基线通过、当前失败。

这说明问题不在 BM25 相关性本身，而在结构加成的施加方式：当加成幅度大于 BM25 差距时，会直接翻转正确排序。

### 2.2 locate 型：passage 排序缺 IDF 与查询噪音词

locate 型回归的表现为 `locate --json` 中 `keywords` / `matched_terms` 被低特异性词或查询噪音词带偏，进而使 passage 排序选中错误片段。

当前 passage 排序缺少词特异性权重，导致常见词、泛化词与真正有区分度的查询词在排序中近似等价。查询侧如果再引入噪音词，错误匹配会被进一步放大。

这一类不能通过削弱 search 侧 `structural_bonus` 解决，需要单独处理：

- locate 侧 passage 排序加入词特异性权重，例如 IDF 类权重
- 查询侧清洗噪音词，避免低信息量词进入 `keywords` / `matched_terms`

## 3. “结构加成封顶 1.0”方案不可行

曾尝试将结构加成统一封顶为 1.0，R7 除外，因为 R7 已有单测锁定。

实验结果：

- 修好 4 对，包括 v09-t158-q01
- 破坏 3 个已修复对：
  - v09-t004-q06「背包 重量」
  - v09-t006-q02「弹力带划船」
  - v09-t009-q06「一个人 安全」

这 3 个 expected 文档恰恰依赖 2.25 ~ 3.5 的结构加成才能获胜。

更关键的是，实测发现不存在统一封顶值能同时满足两侧：

- v09-t064-q08 要求 `cap < 1.155`
- v09-t004-q06 要求 `cap > 2.229`

两者直接矛盾。

结论：**结构加成信号本身不具备区分“好加成 / 坏加成”的能力**。全局削弱结构加成是错误方向，该改动已回退。

## 4. 后续攻坚方向建议

### 4.1 按规则逐条提精度，而不是全局削弱

不要继续寻找统一封顶值或全局缩放系数。应逐条检查结构加成规则，提高触发精度。

优先处理 R3' / R6' 行首家族：

- 收紧“行首命中”的触发条件
- 区分真正的查询意图命中与偶然行首词命中
- 对 R6' 的“行首命中 + 数字”增加数字与查询语义的一致性判断
- 避免仅因某个 token 出现在行首就给予高额结构加成

对于 R1、R2、R2b、R4，也应逐条评估：

- 标题行加成是否要求查询词与标题词更强对应
- 块级同现是否应限制在同一语义块内
- 首段兑现是否应避免与查询弱相关的词重复出现
- 主题前缀是否应要求前缀与查询主题一致

R7 保持现有单测锁定，不作为本轮削弱对象。

### 4.2 locate 侧：passage 排序加入词特异性权重

`locate` 的 passage 排序需要引入词特异性权重，例如 IDF 类权重：

- 高特异性查询词命中应显著高于常见词命中
- 多个低特异性词同时命中不应压倒单个高特异性词命中
- `matched_terms` 的排序和筛选应反映词权，而不是仅反映是否出现

目标：减少“词出现了但词不重要”导致的错误 passage 排序。

### 4.3 查询侧：清洗噪音词

查询侧需要增加噪音词清洗：

- 识别并降低低信息量查询词权重
- 避免噪音词进入 `keywords` / `matched_terms`
- 对明显泛化词、口语填充词、无主题区分度词进行过滤或降权

查询清洗应与 locate passage 排序联动，而不是只在某一侧单独缓解。

## 5. 方法论备注：`search --explain` 的 limit 依赖问题

实测发现：`search --explain` 的排序与 `search` 真实排序可能不一致。

具体表现为 `search --explain` 的 Top1 会随 `--limit` 参数变化。例如 v09-t009-q06 在 `--limit=4` 与 `--limit=10` 下 Top1 不同。

因此后续排序诊断必须遵守：

- 使用与评测一致的默认 limit 运行 `search --explain`
- 或者直接以评测脚本输出为准
- 不要用不同 limit 下的 explain 结果做跨实验比较
