# v09 评测语料第一批失败案例复盘报告

## 一、这份报告要干什么

这份报告回答一个问题：v09 这批评测语料和评测管线跑起来之后，哪些地方会出错、错在哪、按什么顺序修。

它是一份分析框架，不是结论。里面所有"示例"都是构造出来的，用来把分类讲清楚，不代表真实跑出来的结果。真实数字要等人类跑完评测管线之后回填。

### 1.1 先说清楚：这份报告里没有真实评测数字

本文不写"命中率 XX%""MRR 0.XX"这类数字。原因很简单：评测管线刚交付，还没在完整语料上跑过。任何现在写进去的百分比都是编的。

本文能确定的事情只有三件：

1. 评测对的数据结构长什么样（从 `eval_pairs_v09_sample.json` 逐字读出来的字段）。
2. 语料规模是多少（180 个主题簇，约 1400 篇文档）。
3. 失败案例怎么分类、怎么修、先修哪个。

## 二、评测对的数据结构

评测对文件是 `docseek/eval/eval_pairs_v09.json`，抽样文件是 `docseek/eval/eval_pairs_v09_sample.json`。下面按 `eval_pairs_v09_sample.json` 的结构逐字说明字段。

### 2.1 顶层结构

`eval_pairs_v09_sample.json` 是一个 JSON 数组，数组里每个元素是一条评测对。每条评测对描述"给一个 query，应该命中哪些文档，这些文档属于哪个主题簇"。

### 2.2 单条评测对的字段

按字段逐个说：

- `query`：字符串。用户输入的问句，也就是评测时的检索输入。它是一条自然语言问句，不是关键词堆。
- `expected_doc_ids`：字符串数组。这条 query 的预期命中文档 id 列表。列表里第一个 id 是"最该命中的那篇"，排序指标会用到这个顺序。
- `topic_cluster_id`：字符串。这条评测对归属的主题簇 id。180 个主题簇，每个簇有自己的 id，评测对通过这个字段挂到簇上。
- `topic_cluster_name`：字符串。主题簇的可读名字，用来在报告里人肉看结果，不参与计算。
- `notes`：字符串。出题人留的备注，比如"这条 query 有歧义""这篇文档是后来补的"。可以为空字符串。

### 2.3 字段示例

下面是一条评测对的样子。这是构造示例，字段名和 `eval_pairs_v09_sample.json` 保持一致，值是为了讲清楚格式编的。

```json
{
  "query": "怎么把一段长文本按标点切成分句",
  "expected_doc_ids": ["doc_v09_0123", "doc_v09_0124"],
  "topic_cluster_id": "tc_v09_007",
  "topic_cluster_name": "文本分句与切分",
  "notes": "示例，待真实评测运行后替换"
}
```

### 2.4 读这份结构时要注意的点

- `expected_doc_ids` 是有序的。命中率只看"有没有命中"，首位命中率和 MRR 看"命中的是不是排在前面"，所以这个顺序不能乱。
- 一条 query 可以有多个预期文档。多预期文档会让 MRR 的计算需要先定一个约定：取排在检索结果里最靠前的那个预期文档算倒数排名。
- `topic_cluster_id` 和 `topic_cluster_name` 是一对。`topic_cluster_id` 用来分组统计，`topic_cluster_name` 用来给人看。
- `notes` 不参与任何计算，只是备注。

## 三、语料规模

- 主题簇：180 个。
- 文档：约 1400 篇。

语料放在 `docseek/eval/corpus_v09/` 和 `docseek/eval/corpus_v09_parts/` 两个目录下。`corpus_v09/` 是拼好的完整语料，`corpus_v09_parts/` 是分批生成的片段，方便分块处理。

平均下来每个主题簇约 7.8 篇文档。这个数字是估算，因为文档数写的是"约 1400"。

## 四、评测指标定义

三个指标：命中率、首位命中率、MRR。下面给公式，并说明每个符号指什么。

### 4.1 符号约定

- 评测对总数记为 `N`。
- 第 `i` 条评测对记为 `q_i`。
- 第 `i` 条评测对的预期文档集合记为 `E_i`，也就是 `expected_doc_ids` 转成的集合。
- 检索系统对 `q_i` 返回的结果列表记为 `R_i`，是有序列表。
- 检索结果列表的截断长度记为 `K`。比如只看前 10 条，`K = 10`。本文所有指标默认在 `K` 截断下算。

### 4.2 命中率

命中率回答"预期文档有没有被检索到"。

单条 query 的命中标记：

```
hit_i = 1  如果 E_i 与 R_i 的前 K 条有交集
hit_i = 0  如果 E_i 与 R_i 的前 K 条没有交集
```

命中率：

```
命中率 = (Σ_{i=1..N} hit_i) / N
```

值域 0 到 1，越高越好。

### 4.3 首位命中率

首位命中率回答"预期文档里最该命中的那篇，有没有排在第一"。

记 `E_i` 里的第一个文档为 `e_i1`，也就是 `expected_doc_ids[0]`。记 `R_i` 的第一条为 `R_i[0]`。

```
top1_i = 1  如果 R_i[0] == e_i1
top1_i = 0  否则
```

首位命中率：

```
首位命中率 = (Σ_{i=1..N} top1_i) / N
```

值域 0 到 1，越高越好。这个指标比命中率严，它同时要求"命中"和"排第一"。

### 4.4 MRR

MRR 是 Mean Reciprocal Rank，平均倒数排名。它回答"命中的预期文档排得有多靠前"。

单条 query 的倒数排名：在 `R_i` 的前 K 条里，找到第一个属于 `E_i` 的文档，记它的位置为 `rank_i`，位置从 1 开始数。

```
rr_i = 1 / rank_i     如果前 K 条里存在属于 E_i 的文档
rr_i = 0              如果前 K 条里没有属于 E_i 的文档
```

MRR：

```
MRR = (Σ_{i=1..N} rr_i) / N
```

值域 0 到 1，越高越好。命中排第 1 时贡献 1，排第 2 时贡献 0.5，排第 3 时贡献约 0.333，没命中贡献 0。

### 4.5 三个指标怎么配合看

- 命中率低：大概率是语料缺失或者分词失败，预期文档根本没进候选集。
- 命中率高但首位命中率低：候选集里有对的文档，但排序没把它排前面，是排序问题。
- 首位命中率高但 MRR 低：少见，通常说明部分 query 命中很靠前、部分 query 完全没命中，命中分布两极分化，要按主题簇拆开看。
- MRR 单独看没意义，要和命中率一起看。命中率 0.5、MRR 0.4 和命中率 0.9、MRR 0.4 是两种完全不同的病。

## 五、失败案例分类框架

四类：分词失败、排序失败、语料缺失、问句理解失败。

每类下面给 2 个构造示例，示例都注明"示例，待真实评测运行后替换"。这些示例是为了让分类可操作，不是真实评测结果。

### 5.1 分词失败

定义：query 或文档被切词切错了，导致本该匹配的词没匹配上。表现是"人看觉得该命中，系统就是没命中"。

典型触发点：

- 中文没有空格，切词器把复合词切碎。比如"文本分句"被切成"文本"和"分句"两个词，但文档里写的是"分句"。
- 专有名词被切碎。比如产品名、缩写、型号被切开。
- 中英混排边界处理错。比如"Python 分句"被切成奇怪的组合。

构造示例 1：

```
query: "长文本按标点切分句"
expected_doc_ids: ["doc_v09_0123"]
topic_cluster_id: "tc_v09_007"
topic_cluster_name: "文本分句与切分"
notes: "示例，待真实评测运行后替换"
```

假设文档 `doc_v09_0123` 正文里写的是"分句"和"标点"，但切词器把 query 里的"切分句"切成了"切分"+"句"，于是匹配不上"分句"。

构造示例 2：

```
query: "怎么配置 HTTP 超时时间"
expected_doc_ids: ["doc_v09_0451"]
topic_cluster_id: "tc_v09_052"
topic_cluster_name: "网络请求配置"
notes: "示例，待真实评测运行后替换"
```

假设切词器把"HTTP"切成了"H"+"T"+"T"+"P"，或者把"超时时间"切成了"超时"+"时间"而文档里是"超时时长"。

怎么确认是这类：把 query 和预期文档都拿出来，人工看分词结果，看有没有该成一个词的被切开、或者该切开的被粘住。如果分词修对之后命中恢复，就归这类。

### 5.2 排序失败

定义：预期文档进了候选集，但排在 K 条之外，或者排在很后面导致 MRR 低。表现是"命中率还行，但首位命中率和 MRR 上不去"。

典型触发点：

- 词频权重给太高，长文档靠堆词把短而准的文档压下去。
- 缺少字段权重，标题里的词和正文里的词一样重。
- 同义改写没处理，query 用的词和文档用的词是同义但不同形。

构造示例 1：

```
query: "文档去重怎么做"
expected_doc_ids: ["doc_v09_0201", "doc_v09_0202"]
topic_cluster_id: "tc_v09_031"
topic_cluster_name: "文档去重"
notes: "示例，待真实评测运行后替换"
```

假设 `doc_v09_0201` 标题就是"文档去重"，但正文很短，词频低，被一篇长文档挤到第 15 位，K=10 时没进榜。

构造示例 2：

```
query: "语料清洗的步骤"
expected_doc_ids: ["doc_v09_0305"]
topic_cluster_id: "tc_v09_044"
topic_cluster_name: "语料清洗"
notes: "示例，待真实评测运行后替换"
```

假设 `doc_v09_0305` 在榜上排第 3，命中率算命中，但首位命中率算不中，MRR 贡献约 0.333。这类是"命中但不靠前"。

怎么确认是这类：看 `R_i` 里有没有预期文档。有，但位置靠后，就归这类。把位置分布画出来，看是普遍靠后还是个别 query 靠后。

### 5.3 语料缺失

定义：预期文档压根不在语料里，或者语料里有这篇文档但内容不全。表现是"不管怎么检索都命中不了，因为答案不在库里"。

典型触发点：

- 出题时引用了还没入语料的文档 id。
- 文档入库时被截断，关键段落丢了。
- 文档编码或格式解析失败，入库变成空文档。

构造示例 1：

```
query: "v09 主题簇怎么划分"
expected_doc_ids: ["doc_v09_0600"]
topic_cluster_id: "tc_v09_090"
topic_cluster_name: "主题簇划分"
notes: "示例，待真实评测运行后替换"
```

假设 `doc_v09_0600` 在 `expected_doc_ids` 里写了，但 `corpus_v09/` 里没有这个 id 的文件。

构造示例 2：

```
query: "评测管线怎么跑"
expected_doc_ids: ["doc_v09_0712"]
topic_cluster_id: "tc_v09_101"
topic_cluster_name: "评测管线使用"
notes: "示例，待真实评测运行后替换"
```

假设 `doc_v09_0712` 在语料里存在，但文件是空的，或者只有标题没有正文。

怎么确认是这类：拿 `expected_doc_ids` 去语料目录里逐个对，看 id 在不在、内容全不全。这类问题不该靠调检索算法修，要靠补语料修。

### 5.4 问句理解失败

定义：query 本身有歧义、指代、省略，检索系统按字面匹配，抓错了方向。表现是"系统命中了别的主题簇的文档，而且命中的文档单看 query 字面也不算错"。

典型触发点：

- query 里带指代，比如"它怎么用"，指代对象在上下文里，但评测时只有这一句。
- query 一词多义，同一个词在不同主题簇里指不同东西。
- query 是省略句，缺主语或宾语，字面匹配抓到不相关的簇。

构造示例 1：

```
query: "这个参数怎么调"
expected_doc_ids: ["doc_v09_0801"]
topic_cluster_id: "tc_v09_115"
topic_cluster_name: "检索参数调优"
notes: "示例，待真实评测运行后替换"
```

"这个参数"没有指代对象，字面匹配可能命中任意讲"参数"的文档。

构造示例 2：

```
query: "批量处理慢"
expected_doc_ids: ["doc_v09_0855"]
topic_cluster_id: "tc_v09_122"
topic_cluster_name: "批处理性能"
notes: "示例，待真实评测运行后替换"
```

"批量处理慢"可以指性能问题，也可以指排队等待，字面匹配容易抓到讲"慢查询"的文档，而不是讲批处理的。

怎么确认是这类：把误命中的文档拿出来看，如果它单看 query 字面也说得通，但和预期文档不是一个主题簇，就归这类。这类要靠改 query 写法或者加同义扩展修，不是靠调分词。

### 5.5 四类怎么分优先级

分类不是互斥的。一条失败的 query 可能同时有分词问题和排序问题。处理顺序是：先看语料缺失，再看分词失败，再看问句理解失败，最后看排序失败。

理由：语料缺失是数据问题，不修的话后面全白搭。分词错了，排序再对也匹配不上。问句理解错了，修分词也救不回来。排序是最后调的，因为前三个都修好之后，排序问题才看得清楚。

## 六、调优 backlog

按"分词 → 排序 → 问句理解"排优先级。每项写预期收益和验证方法。

### 6.1 第一优先级：分词

要修的东西：

- 把 query 和文档走同一套切词器，确认两边切法一致。
- 把主题簇名字里的核心词加进自定义词典，比如"分句""去重""主题簇"。
- 中英混排单独处理，英文缩写、型号、版本号不要被切开。
- 数字和单位连写不要切散，比如"10ms"不要切成"10"和"ms"。

预期收益：修完能救回 5.1 里那类"人看该命中、系统没命中"的 case。命中率会先涨，因为候选集里开始出现对的文档。

验证方法：拿 5.1 的构造示例改成真实 case，跑评测管线，看这批 case 的 `hit_i` 从 0 变 1。同时跑一遍不相关的 case，确认没把原本命中的弄丢。

### 6.2 第二优先级：排序

要修的东西：

- 加字段权重，标题命中的权重要高于正文命中。
- 给长文档做长度归一，别让堆词的长文档压过短而准的文档。
- 对 `expected_doc_ids` 里排第一的文档，看它在榜上的位置分布，位置普遍靠后的话加个精排。

预期收益：修完能救回 5.2 里那类"命中但不靠前"的 case。首位命中率和 MRR 会涨，命中率可能不动。

验证方法：跑评测管线，看 `rr_i` 的分布。如果一批 case 的 `rank_i` 从 10 开外挪进前 3，说明排序修对了。同时确认命中率没掉。

### 6.3 第三优先级：问句理解

要修的东西：

- 对带指代的 query，在评测对里补上下文，或者把 query 改写成完整句。
- 对一词多义的 query，用 `topic_cluster_id` 做约束，限制检索范围在同一个主题簇内。
- 对省略句，加同义扩展，把省略的部分补回来。

预期收益：修完能救回 5.4 里那类"字面说得通、主题不对"的 case。命中率和首位命中率都会涨。

验证方法：跑评测管线，看误命中到别的主题簇的 case 是不是变少。具体做法是统计每条 query 命中的文档里，有多少属于它自己的 `topic_cluster_id`。

### 6.4 语料缺失单列，不排进上面三个

语料缺失不属于算法调优，属于数据修复。它应该在跑完第一轮评测之后立刻处理：把 `expected_doc_ids` 里在语料中找不到的 id 列出来，该补的补，该改评测对的改评测对。

验证方法：写一个检查脚本，遍历所有评测对的 `expected_doc_ids`，逐个去 `corpus_v09/` 里对 id，输出缺失清单。这份清单要清零。

## 七、怎么用这份报告

1. 先跑评测管线，拿到真实结果。管线脚本在 `docseek/eval/` 下，是 python 写的。
2. 把真实失败 case 按第五节的四类归类，替换掉本文里的构造示例。
3. 按第六节的优先级修，每修一项跑一次评测，记录指标变化。
4. 把回填后的数字和本文的框架合并，形成下一版报告。

再说一遍：本文没有真实评测数字，第五节所有示例都标了"示例，待真实评测运行后替换"。谁要是把本文的示例当真实结果用，那是用错了。
