# 检索路径停用词过滤设计（GAP-STOPWORD-001）

## 1. 问题陈述

`src/query_parser.cpp` 中已存在单字停用词表 `singleCharStopwords()`，并通过公开函数
`bool isSingleCharStopword(const std::string& w)`（声明于 `include/docseek/query_parser.h`）对外暴露。
该函数在自然语言路径 `parseNaturalQuery`（供 `/api/locate` 使用）中已被调用，单字停用词会被过滤。

但 FTS 检索路径 `Searcher::search` 与 `Searcher::searchQuestion` 使用各自的 `splitTokens`
分词，分词结果未经过 `isSingleCharStopword` 过滤，导致停用词直接进入后续阶段并参与打分与排序。

### 实测行为（当前，未修复）

1. `search '的'` → 返回 1 hit（期望：空结果）。
2. `search '了 在 的'` → 返回 1 hit（期望：空结果）。
3. `search '的 苹果'` → 首位是含“的”的文档，而非“苹果”文档（停用词污染排序）。

这三条现象共同构成本次修复要覆盖的核心缺口 GAP-STOPWORD-001。

### 停用词表内容（现状，不改动）

`singleCharStopwords()` 当前包含：
的 / 了 / 在 / 是 / 有 / 和 / 与 / 或 / 个 / 上 / 下 / 中 / 之 / 为 / 于 / 由 / 把 / 被 / 给 / 对 / 就 / 都 / 也 / 还 / 要 / 会 / 可 / 以 / 及 / 得

“不”字不在该表中，属于否定语义保护，本设计不触碰。

## 2. 过滤点位置

过滤统一放在 `Searcher::search` 与 `Searcher::searchQuestion` 的**入口处**，即 `splitTokens`
产出 token 序列之后、任何阶段逻辑之前：

- 对 `splitTokens` 得到的每个 token，若 `isSingleCharStopword(token)` 为真则丢弃。
- 只判断**整个 token** 是否为单字停用词，不拆分多字 token。

选择入口而非各阶段的理由：

1. **一致性**：三阶段与 `rerankHits` 若各自过滤，极易出现遗漏或重复过滤，导致同一查询在不同路径下
   行为不一致；入口处统一过滤可保证下游看到的是同一份干净 token 序列。
2. **可预测性**：入口过滤后，token 序列即为该次查询的“有效查询词”，下游阶段无需再关心停用词，
   降低维护成本。
3. **避免重复代价**：过滤是 O(n) 且极廉价，放在入口只做一次；若分散到各阶段会被重复执行。
4. **空查询早返回**：过滤后可能为空，需要在打 FTS 之前判定并短路，入口是最自然的短路点。

## 3. 纯停用词查询的返回约定

过滤后若有效 token 为空（即查询全部由单字停用词构成，如 `'的'`、`'了 在 的'`）：

- **直接返回空结果**，不调用 FTS 检索。
- 与“无匹配”的空结果在结构上保持一致（不抛异常、不返回错误码），仅结果集为空。
- 不因空 token 触发任何阶段逻辑或 `rerankHits`。

该约定同时覆盖单停用词查询与多停用词查询，两者行为一致。

## 4. 对三阶段与排序的影响分析

过滤后的 tokens 贯穿三阶段与 `rerankHits`：

- **三阶段检索**：各阶段使用的 token 序列均为过滤后的结果，停用词不再作为检索词参与匹配，
  因此不会再因“的/了”这类词命中无关文档。
- **`rerankHits` 标题加成**：标题加成基于过滤后 tokens 计算，含停用词的文档标题不再因停用词
  获得加成。
- **`rerankHits` 短语加成**：短语加成同样基于过滤后 tokens 计算，避免停用词构成虚假短语匹配。

综合效果：`search '的 苹果'` 的有效 token 仅剩 `苹果`，排序由“苹果”决定，不再被“的”的命中
拉偏，从而修复实测用例 3。

## 5. 已知限制

- **多字 token 内部的停用字不处理**：例如 `新的了` 尾部的“了”属于多字 token 的内部字符，
  本设计只判断整个 token 是否为单字停用词，不拆分多字 token，因此不会移除。
  此类长问句噪音归入 D 类后续排期，本轮不动。
- **“不”不在停用词表**：否定语义受保护，本设计不修改停用词表内容，也不对“不”做任何特殊处理。
- **自然语言路径不在本次范围**：`parseNaturalQuery`（`/api/locate`）已过滤单字停用词，
  本设计只改 `Searcher::search` 与 `Searcher::searchQuestion` 两条 FTS 路径。

## 6. 测试计划要点

测试应基于真实可验证行为，覆盖以下要点：

1. **单停用词查询**：`search '的'` 返回空结果（覆盖实测用例 1）。
2. **多停用词查询**：`search '了 在 的'` 返回空结果（覆盖实测用例 2）。
3. **混合查询排序**：`search '的 苹果'` 首位为“苹果”文档，而非含“的”的文档（覆盖实测用例 3）。
4. **停用词不参与标题加成**：构造标题含停用词的文档，确认其不因停用词获得加成。
5. **停用词不参与短语加成**：确认停用词不构成虚假短语匹配。
6. **多字 token 内部停用字保持现状**：`新的了` 类 token 不被拆分或裁剪，验证已知限制行为。
7. **“不”语义保护**：确认“不”仍作为有效 token 参与检索，未被过滤。
8. **空 token 短路**：确认纯停用词查询不触发 FTS 调用（可通过打点或桩验证）。
9. **两条路径一致性**：`Searcher::search` 与 `Searcher::searchQuestion` 对同一停用词查询
   返回一致结果。

断言必须基于上述可观测输出（结果集、顺序、是否调用 FTS），不写无法验证的期望。
