## 2. 表结构 schema

### 2.1 合同 struct（不可改）
```
struct SynonymEntry {
    const char* term;                       // 精确匹配键，UTF-8 小写
    const char* const* expansions;          // 展开词数组，UTF-8
    int expansionCount;                     // 展开词数量
};
const SynonymEntry* findSynonyms(const char* term);  // 命中返回，否则 nullptr
```

字段语义：
- `term`：查询侧 token（经疑问词剥离 + 停用词过滤后仍在的实词）。**大小写不敏感匹配由调用方归一化保证**，表内以原文形态存储。
- `expansions`：与 `term` 构成 OR 组的同义片段。**不含 `term` 自身**——调用方在拼 FTS5 片段时显式保留原 token，避免表内重复。
- `expansionCount`：必须 > 0；等于 0 的条目为非法条目，构建期即拒绝。

### 2.2 为什么是精确匹配
- 前缀匹配会让「花费」误命中「花费用」「花费心思」等 query 侧 token，把 AND 语义悄悄放宽为 OR，直接制造召回膨胀。
- 模糊匹配（编辑距离 / 拼音）需要引入额外依赖与阈值调参，与本表的"白名单最小化"原则冲突，收益边际为零。
- 本表是白名单：只收录经 corpus 证据验证的词对。精确匹配是"白名单"语义的最直接实现，读代码的人一眼能判断某 token 会不会被展开。

### 2.3 排序与去重
- `expansions` 内部顺序即 FTS5 OR 组内顺序，无排序语义；为保证可复现，按 UTF-8 字节序升序存储。
- 同一 `term` 在全表中只允许出现一次；`expansions` 内不得重复；`expansions` 不得包含 `term` 自身。构建期静态断言 + 单测校验。

## 4. 加载策略

### 4.1 最小版本：编译期常量表
`src/synonyms.cpp` 内 `static const char* const kExp_*[]` + `static const SynonymEntry kTable[]`，`findSynonyms` 做线性扫描（3 条以内，成本可忽略）。`#include "docseek/synonyms.h"` 暴露接口。

### 4.2 演进路线对比（本轮不采用）
- **配置文件（JSON/TOML）**：需要新增解析依赖、启动期加载与错误处理、热更新语义；3 条表换来一整套 IO 与校验代码，构建复杂度上升。发版时表与二进制不同步，回滚需同时回滚文件。
- **DB 表（SQLite）**：需要 schema 迁移、写入工具、与现有 FTS5 索引的版本一致性管理；同义词是纯逻辑常量，放 DB 只会引入状态。

### 4.3 结论
最小版本选编译期常量：与二进制同发版、原子回滚、零运行时依赖、评审时全表可见。等表规模超过 ~200 组或需要运营侧维护时，再评估配置文件路线。

## 5. 查询展开

#### 5.1 同义词展开点

同义词展开发生在 `src/searcher.cpp` 的 `expandTokenWithJoiner` 内部，处于 `CutForSearch` 切词 + `claimTokenPositions` 按起始字节偏移分组**之后**。具体机制如下：

1. 对 `groups` 中每个起始偏移分组，组内的每个词（词粒度，来自 jieba `CutForSearch`）以精确匹配方式查同义词表 `findSynonyms`。
2. 命中后，该词的 `expansions` 与组内原词**并入同一个 OR 组**，最终由 `groupExpr` 生成 `("花费" OR "多少钱")` 形式的片段。
3. 未被 `claimTokenPositions` 认领的词（`unclaimed` 列表）同样查表；命中则输出 `("原词" OR "扩展1" OR "扩展2")` 的 OR 组，未命中则退化为 `quoteToken(w)`（与原来一致）。
4. 展开**仅当组内/未认领词中出现表内词时才激活**；其余情况生成的查询串与未启用同义词时一字不差。

**为什么必须是词组级，而不是 token 级：**

中文查询多为无空白单 token（如 `"通勤装备花费"`）。`splitTokens` 对整个查询切出来的就是**一个 token**，对这个整 token 做精确同义词表匹配永远命中不了表内词——`"花费"` 只是该 token 的**子串**，而非等值。上一轮采用 token 级方案时，3 个 `BSynonym` 单测实测为红（返回空结果），已实证证伪。

正确层级是**词组级**：先 `CutForSearch` 把整 token 切为词（`"通勤"`、`"装备"`、`"花费"`），再在组内对每个**词**精确查表。示例：

```
"通勤装备花费"  →  "通勤" AND "装备" AND ("花费" OR "多少钱")
```

由于 `buildMatchQuery` / `buildOrMatchQuery` / `expandTokenOrSingle` 三者均调用 `expandTokenWithJoiner`，词组级展开对这三条路径**自动生效**，无需各自改造。

**约束（红线）：**

- `expansions` 已是词粒度，直接 `quoteToken` 输出；**不得**再走 `expandTokenOrQuery` 二次展开。
- **不得**对 expansions 递归查表（禁止画蛇添足的多级展开）。
- `expansionCount` 为 `int`，循环变量使用 `int`，避免 `-Wall -Wextra` 下 `int`/`size_t` 比较告警。
### 5.2 展开粒度
词组级 OR 组（B3-r2 修正：原 token 级方案被单测证伪）。**词组之间仍是 AND**。这保证「通勤装备花费」在展开后是 `"通勤" AND "装备" AND ("花费" OR "多少钱")`，而不是整体 OR，避免把任一词的匹配都当命中。

### 5.3 不在索引侧做
- 索引膨胀：每篇文档的每个可展开词都要写多份 postings，存量索引全量重建。
- 存量索引重建成本：v09 corpus 已有版本化索引，重建会污染版本管理，且回滚需要重建。
- 查询侧展开只影响本次查询的 match 表达式，索引零改动。

### 5.4 不用 embedding / 向量
项目无向量 infra，SQLite FTS5-only 是既定架构。引入向量检索等于新增索引格式、相似度阈值调参、embedding 模型版本管理，与 v0.16.0 的边界不符。

## 6. 「区别」类措辞差异单独论证

v09-t022-q04「bounce和rock区别」→ v09_t022_04.html，**本轮不修**。

事实核对：
- 期望文档标题「街舞基础步伐：bounce和rock怎么入门」。
- 正文 bounce 出现 8 次、rock 出现 8 次。
- **「区别」出现 0 次**。

论证：
1. 同义词表的作用是「query 中的 token t，在文档里以同义词 e 出现」。此对中 query 的判别 token「区别」在文档里出现 0 次，展开任何词都不会让 `frag(区别) OR frag(e)` 命中——因为文档里既没有「区别」，也没有任何「区别」的同义表达。展开无法凭空创造判别信号。
2. 该 query 的真实意图是「A 和 B 两个概念的对比」。判别信号是 bounce 与 rock 在同一文档共现，而不是「区别」这个词。
3. 因此正确的机制是**问句模式改写**：识别「A和B区别/对比/差异/哪个好」模式，改写为「A B」并去掉模式词，再走既有 AND 检索。这属于查询改写层，与同义词表是两套机制，不应混入本表。
4. 若强行把「区别」写入表，任何含「区别」的 query 都会被放宽，且对本文档依然无效——既是无效方案，也是误伤来源。明确拒绝。

未来设计要点（v0.16.0 不实现，仅记录）：
- 模式库需以正则/模板形式集中在查询改写层，与同义词表物理隔离。
- 改写需保留原 query 用于日志与回归对比，避免误改写掩盖真实召回退化。
- 改写后仍走同一 AND 链路，禁止在此层引入新的召回路径。

结论：v09-t022-q04 列为诚实边界，v0.16.0 不修。

## 7. 风险与控制

- **召回膨胀**：白名单最小表是控制手段。当前仅 3 条，且每条都有 corpus 证据。任何新增条目必须附带失败样本编号与文档核对记录。
- **语义漂移**：精确匹配避免「花费」误伤「花费用」这类 query token——后者不查表，语义不被改写。
- **否定保护**：「不」永不入表是既有铁律。本表 3 条不含任何否定词。
- **与 fillerWords / 单字停用词的交互顺序**：**先疑问词剥离 → 再停用词过滤 → 最后同义词展开**。理由：
  - 疑问词（如「吗」「呢」）剥离后才能拿到干净的实词 token，避免把疑问词当 term 查表。
  - 停用词过滤先做，保证进入展开的 token 都是实词，避免对「的」这类 token 做无意义查表。
  - 展开放在最后，是因为展开只影响 match 表达式构造，越靠近 `buildMatchQuery` 越容易做局部验证。
