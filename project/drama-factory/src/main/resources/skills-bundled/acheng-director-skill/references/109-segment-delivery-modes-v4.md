# 109｜Segment 分段交付模式 v4

## 首次调用必须先选择

Acheng Director 新建一次生产运行时，先只发送下面的固定选择题，不开始剧本、资产或 H3 正文生产：

```text
本次长内容交付请选择一种方式（默认推荐 1）：

1. 自动文件批处理模式（默认/推荐）：在宿主提供工作区写入能力时，自动逐段生成独立的 `.h3.txt`、资产提示词或合同文件，保存 SHA-256、状态和游标；聊天直接展示逐段上传操作卡，并附 manifest、文件与验收结果。适合一次提交后离开，但仍受宿主运行时长、工具调用、权限和磁盘限制。

2. 交互制作模式：每轮只输出并提交一个完整 Segment；提交后暂停，方便用户即时调整角色、空间、战斗方向和参考图。我回复“继续”或“下一段”后，再输出下一个 Segment。

请回复 1 或 2。未选择前不要开始正文生产。
```

选择只对本次 `run_id` 生效。继续同一次运行时读取 `workflow_state.execution_mode`，不要重复询问，也不能静默改变模式。新建另一项任务或清空运行状态后重新询问。

## 模式 1：autonomous_file_batch（默认）

- 先创建计划、`workflow_state.json` 和输出目录，再按 Segment 顺序生成独立文件。每个 Segment 不能只存在于聊天输出里。
- 每份文件独立包含完整模式字段、主体、场景、状态、动作因果、空间位置、朝向、微动作、微表情、接触/受力、相机、声音和尾态；不能以“同上”依赖上一文件。
- 每份文件由 `orchestrator_commit.py` 计算 SHA-256、原子写入、记录 `input_revision` 和 `output_revision`。partial 文件必须保留 `current_cursor` 且 `accepted=false`。
- 聊天直接展示逐段上传操作卡，并附 manifest、文件与验收结果、文件路径、每个文件的状态、哈希、未决项和 visual_status；不要把已经写入文件的长正文再次全部贴回聊天。
- 该模式不是无限后台任务。宿主没有工作区写入工具、工具循环被中断、权限不足、磁盘失败或上下文预算耗尽时，必须保存已提交文件并暂停，明确下一步；不能声称“已自动完成”。

## 模式 2：interactive_segment

- 先完成总控台、能力触发图和必要的生产骨架；正文阶段每轮最多一个完整 Segment。
- Ref2VA `detailed_description` 使用按 Segment 时长与复杂度计算的动态密度门；默认 10 秒段最低 2,000、目标约 2,400 个英文词，超出单次上限时按字段、镜头和游标继续，不把未完成 Segment 当成完整交付。达到宿主上限时按字段、镜头和游标继续，不把未完成 Segment 当成完整交付。
- 当前 Segment 只有在 H3 字段、上传清单、连续性和机器检查完成后才提交；提交后暂停。
- 用户回复 `继续` 或 `下一段` 时，从下一个未提交 Segment 或保存的 `current_cursor` 继续。其他修改意见先回到对应字段，不得丢失已提交产物。
- 如果用户在一句话里要求“继续全部”，仍遵守每轮一个 Segment；可以在回执中列出剩余数量，但不能一次倾倒全部正文。
- `/goal` 不改变这条边界：目标可以跨多个回合持续，但本回合提交一个 Segment 后必须停止，并返回 `WAIT_FOR_USER_CONTINUE`；不要把 goal 的完成条件误写成单轮完成条件。

资产任务仍遵守 STYLE_MOTHER 前置；H3-only 仍不启动资产分支。交付模式改变的是交付载体和推进方式，不改变模块权属和质量门禁。

## 统一禁止项

两种模式都禁止：降低 Ref2VA 词数、把多个 Segment 合成摘要、静默切换 H3 模式、把 partial 标记 accepted、伪造生成媒体、覆盖旧 artifact、使用过期 production revision，或把工具计划描述成真实媒体已经生成。
