# 94｜交付完整性与反省略门

本门是 Acheng 的执行层协助，不是第二套导演、调度器或提示词编译器。它吸收红猴子体系中有用的反省略与诚实声明机制，只做交付前阻塞检查；不写 production 真值，不改剧本、ShotSpec、资产卡或 H3 正文。

## 适用范围

每次准备向用户交付一个阶段或一个完整包时运行一次。阶段可以是剧本、分镜、表演、动作、视效、资产、H3、Seedance、续作或审计。已有确认稿的阶段仍要检查本次范围，不得因为“前面做过”而把当前缺项吞掉。

## 五项不可省略检查

1. **范围锁定**：先写清本次请求的阶段、交付范围和未覆盖范围。只做资产或一段 H3 时，不得声称整剧完成；`prompt_only` 不得写成 `full_production`。
2. **最小完整单元**：交付物必须达到该阶段的最低可用单元。剧本要有场景、节拍和对白；分镜要有闭合时间轴和镜头事件；资产要有完整 `.image.txt`、参考图策略和上传清单；H3 要有模式正确、逐段独立的完整正文。提纲、摘要、字段目录、下载链接或“后续补充”不能冒充完成。
3. **反省略**：模型正文不得用“同上、如上、沿用前段、根据需要调整、若干动作、等等、见角色设定”替代本次事实。必须逐条写出主体、场景、状态、动作、摄影、声音、尾态和必要的因果链。合法的 H3 `<Picture N>`、`<Subject N>`、`(S1)` 以及用户原对白不属于偷懒代号，但其定义和槽位仍须完整。
4. **证据诚实**：每个“已完成、PASS、可提交”都绑定实际文件、字段或机器检查。没有调用生成模型不能写成已生成；没有人工画面检查不能写成画面通过；缺图、未定对白、未验证能力必须显式保留在 `execution_gate` 或 `unresolved`。
5. **失败传播**：发现缺项时返回具体路径、影响和下一步，状态使用 `NEEDS_DIRECTOR_REVISION` 或 `EXECUTION_BLOCKED`。不得为了得到更短或更漂亮的答复删除真实约束、降低提示词细节或把未知猜成已知。

## 不得造成的副作用

- 本门不能按字数截断、压缩、摘要化或重写模型正文；完整 H3/资产提示词优先级高于交付视图的简洁性。
- 本门不能强制固定时间轨、固定风格、固定镜头编号或固定“五轨秒数”；这些由题材、ShotSpec、模型合同和实际时长决定。
- 本门不能把内部 Previs、资产、人物或情绪 ID 添加进模型正文；它只能检查这些 ID 已在正文外展开或在合法 H3 参考语法中正确定义。
- 本门不能启动后台任务、代理、联网或付费生成，也不能把“执行建议”伪装成已执行。

## 回执格式

交付回执至少包含：`scope`、`delivered`、`blocked`、`evidence`、`unresolved`、`next_action`。没有阻塞时也要明确写“无”；没有真实媒体时保留 `UNVERIFIED`。回执是门禁证据，不替代任何 `.image.txt`、`.h3.txt`、生产卡或机器 JSON。

## 确定性入口

H3 引用缺项现在直接阻塞“正式交付”，不能被默认 unresolved 披露伪装为可提交。草案仍可保存完整正文、计划及卡片。最终 H3 包还必须运行[114 联合门](114-reference-binding-delivery-v4.3.6.md)核对实际正文、逐段卡、manifest 和聊天视图；production 审核不能代替最终文件检查。

`scripts/delivery_integrity.py <stage> <production.json>` 是本门的只读执行入口。`stage` 使用 `script`、`storyboard`、`perform`、`action`、`vfx`、`assets`、`h3-compile`、`continue`、`audit` 或 `full`；它只读取生产数据和已登记参考文件，输出上述回执，不写回输入。`full` 必须声明 `delivery_scope: full_production`；`--require-ready` 才会把未解决参考图或未验证媒体升级为阻塞，默认仍把这些事实保留在 `unresolved`。模型正文中的“同上／如上／沿用前段”等省略 shorthand 会直接阻塞，用户对白原文不扫描。

## 与红猴子技能的关系

`lobster-task-layer-executor` 的 L1–L4 排程、后台任务暗示和第二调度器继续禁用。这里只选择性吸收它的反省略思想，并与 `lobster-self-reflection` 的证据诚实检查合并为一次主导演门禁。该门的 `write_paths` 必须为空；若检查与创作内容冲突，以用户确认稿、专业模块 owner 和模型语法合同为准。
