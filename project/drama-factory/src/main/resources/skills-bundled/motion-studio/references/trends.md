# Trend radar

`scripts/trends.py` answers one question: which videos in a niche are doing far better than their creator usually does? That ratio, a video's views over the median of the same creator's other recent videos, is the "outlier score" paid tools sell. A 3x video from a 5,000-view creator is a stronger topic signal than a 2M-view video from a creator who always gets 2M.

## Commands
- `trends.py tiktok @a @b` or `--watchlist file.txt` (one handle per line, `#` comments): pulls each creator's recent videos (`--per-creator 30`) and ranks the breakouts.
- `trends.py tiktok-tag scam`: pulls a hashtag's videos (`--videos 60`), then each creator's recent videos for the baseline. Only the hashtag's videos are ranked.
- `trends.py youtube "tiktok scam" --days 14`: searches YouTube for the most-viewed recent videos on a query, then pulls each channel's latest uploads for the baseline.
- `tiktok` drops creators with no post in `--stale-days 60` (0 keeps all) and, with `--keywords scam,fraud`, creators whose videos are under `--min-fit 0.3` on-niche, matching the whole caption and its hashtags, not only the title; it lists every creator it drops. `--keep @a,@b` (the runner's `keep` input) keeps named creators whatever either filter says. The keyword match is crude: on 2026-10-17 it dropped @topclassactions and mkbhd, so keep the creators you know belong. Every report has a Paid column. It shows `declared` when YouTube reports paid product placement, or else the first sponsor marker found in the caption or description (`#ad`, `#sponsored`, `#partner`, "paid partnership", "sponsored by", "use code", "promo code"...). A marker straight after "not" or "no" doesn't count. TikTok's own branded-content label isn't available through yt-dlp, so TikTok flags come from captions only. A sponsored breakout may be paid reach, not demand. The runner's log counts the flagged breakouts per query. `--max-age-days 30` ranks only videos inside the window, while each creator's baseline still uses all of their videos.
- All three write `trends-<date>-<label>.md` (ranked table) and `.json` (every video seen) to `--out` (default `research/trends`). `--min-score 3` is the breakout threshold. Videos younger than `--min-age-days 1` get no score.

## Sources and their limits
- **TikTok** goes through yt-dlp (`python3 -m pip install yt-dlp`), with no account or cookie. It is unofficial, so it breaks in two different ways. If TikTok bot-checks the IP (a home IP that scans often gets this), every page fails and each failure is tagged `[bot-check]`. Upgrading yt-dlp won't help: wait, run from another network (the GitHub runner below), or give the creator's secUid on its watchlist line (`@handle tiktokuser:<secUid>`), which still worked from a bot-checked Mac on 2026-10-17. A secUid must be `MS4wLjABAAAA` plus 64 characters; anything else is skipped with a warning, because yt-dlp would read it as a handle. A line with both is tried by secUid first and by @handle second, so it never does worse than the plain handle. On a GitHub runner on 2026-10-17, all 29 secUid lines failed (`[other]`) while plain handles worked; the Mac where they worked had `yt-dlp[default,curl-cffi]` (browser impersonation), so the runner now installs that too. Locally, `python3 -m pip install -U "yt-dlp[default,curl-cffi]"`. If TikTok changed its site, failures are tagged `[other]`, and `pip install -U yt-dlp` is the first fix. A creator whose page fails is reported and skipped. Tested live on a GitHub runner on 2026-10-16: creator pages worked without a cookie (views and uploader came back), but hashtag pages failed with "No working app info is available", because yt-dlp's hashtag extractor needs TikTok mobile-app credentials. Until that changes, build a watchlist of creators per niche and use `tiktok`, not `tiktok-tag`. Scraping is against TikTok's terms; without a login, the exposure is an IP block, not a banned account.
- **YouTube** uses the official Data API v3 with a free API key (Google Cloud Console > APIs & Services > Credentials > Create API key, then enable YouTube Data API v3). The quota is 10,000 units a day; a search costs 100 and every other call 1, so one query with 25 channels uses about 150. The key goes in `YT_API_KEY` or `~/.motion-studio/youtube/api_key`, never in the repo.
- **Network:** tiktok.com is blocked from the default cloud container. Run TikTok scans on the owner's Mac or in a cloud environment that allows tiktok.com. googleapis.com is reachable from the cloud.

## How to use the results
- The score picks topics. It is not a reason to copy footage. The episode is original: narration, figures, and at most a few credited seconds for commentary. See `longform.md`.
- Prefer topics with a story that lasts (scams, money, people, mysteries) over dances and sounds. A trend that will be dead before the episode ships is a Short at most.
- Read the median column: a breakout against a tiny median (under about 1,000 views) is noise until it repeats.

## On a GitHub runner
TikTok rate-limits an IP that scans often (the owner's Mac was limited on 2026-10-17), so `.github/workflows/trend-radar.yml` runs the `tiktok` scan on a GitHub runner, one niche per run, started by hand (Actions > trend-radar > Run workflow, or the API's workflow dispatch) with `niche`, `handles` or `watchlist`, `per_creator` and `min_score`. The workflow has to be on the default branch before it can be started. Runner IPs are shared and can be blocked too; the log counts the creator pages that failed.

The repo is public, so run logs and artifacts are public. By default (`output: encrypted`) the log shows only counts, and the results leave the runner as `radar-<niche>.tgz.gpg`, encrypted with the `RADAR_KEY` repository secret and kept 7 days. To read them: `gh run download <run-id> -n radar-<niche>`, then `gpg -d radar-<niche>.tgz.gpg | tar -xzf -` with the same passphrase. `output: public` prints the ranked table and uploads plain files. That's handles, titles and view counts, all public on TikTok already, but it shows which niches the channel is watching. The dispatch inputs (niche label, handles) show on the run page either way.

`source: youtube` runs `trends.py youtube` for each of `queries` (separated by `;`) over the last `days`, with the Data API key from the `YT_API_KEY` repository secret, and the same encrypted or public output. A search costs 100 units and the channel baselines about 50 more, so one query is about 150 of the 10,000 free daily units: 5 niches × 2 queries is about 1,500 a day. The key goes to Google in a request header, never in a URL.
