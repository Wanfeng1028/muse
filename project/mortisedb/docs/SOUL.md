# 榫卯 MortiseDB · 灵魂一页纸

## 一句话差异化命题
**NAS 玩家和小团队的本地数据拼装层**：把散落在 SQLite、CSV、JSON、文件夹里的家底，用一份 YAML 声明式地"卯"成一张张表，增量同步、冲突可断、类 SQL 建视图——Airbyte/dbt 对个人太重，Metabase 只读不解决拼装，这是真空位。

## 技术含金量点（不是 CRUD 换皮）
1. **多源 schema 推断与类型统一**：CSV/JSON/目录三种半结构化源，采样推断列类型（整数/浮点/布尔/日期/文本），冲突类型自动提升（int→float→text），日期多格式归一。
2. **真增量同步**：`updated_at` 水位线下推到各连接器（SQLite 走 WHERE，CSV/JSON 走行过滤），无时间列的源退化为整表哈希比对；水位线持久化，断点续跑。
3. **冲突模型**：同一主键多源写入时，按源优先级自动裁决或挂起人工处理，冲突明细可查、可逐条解决——这是"拼装"场景真正的硬骨头。
4. **单二进制 + 纯 Go SQLite**：扔进 NAS/软路由/旧笔记本就能跑，零依赖，数据落本地文件可 Git 版本化。

## 视觉概念
"榫卯"即中国传统木作不用一钉一铆、凹凸相合——正如把异构数据源严丝合缝地拼起来。
UI 走**宣纸 + 墨 + 木赭**：宣纸底 `#F4EFE3`、墨字 `#211C15`、木赭 `#8A5A33`、朱砂点缀 `#B3402A`；
页眉用 CSS 画一道榫卯结构线（凹凸咬合的几何纹），标题用衬线中文（Noto Serif SC 回退宋体）；
左对齐排版，信息密度高，像老师傅的工具箱，不做"科技感"。

## 命名理由
- **榫卯 (sǔn mǎo)**：不用钉子的接合术 = 不用重型数仓的拼装术，意象精准且好记。
- 英文 **MortiseDB**：mortise 即"榫眼"，DB 点明品类，GitHub 上无重名（已核验），域名/包名干净。
- 用户（NAS 玩家、独立开发者）一看就懂：这是个"把东西拼起来"的工具。

## 自查：用户看了会不会眼前一亮？
- ✅ 名字有记忆点，"榫卯拼数据"意象成立，不是"又一个 ETL"。
- ✅ 一句话能讲清跟 Airbyte/dbt/Metabase 的区别，差异化真实（市场调研已砍掉 6 个有强者的方向，这个方向是真空）。
- ✅ 技术点落在算法与工程（类型提升格、水位线下推、冲突裁决），不是"多语言 CRUD"。
- ⚠️ 风险：v1 若只做到"能同步"，亮度会打折——必须把**冲突处理 + 视图查询 + 定时调度**做进 v1，形成"配好 YAML 就不用管"的闭环。
- 结论：开工。v1 按"闭环"标准验收。
