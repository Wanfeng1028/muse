# 调度器部署说明

## 结论

second-brain 的推送调度器跑在进程里，状态存在本地 SQLite 单文件库里，数据目录由环境变量 `SB_DATA_DIR` 指定，默认 `data`。这两点决定了 second-brain 是单实例应用：同一时刻只能有一个实例跑 scheduler，否则会出现重复推送和数据库锁征用。

## 为什么是单实例

- 调度循环是进程内的 goroutine，没有跨进程的协调机制。
- 推送任务的去重和状态记录都在本地 SQLite 文件里，多个进程各写各的，互相看不到对方刚写入的状态。
- SQLite 是单文件库，同一文件多进程写会互相争抢文件锁。

## 合规部署方式

### 方式一：单副本 + 数据卷

只跑一个 second-brain 副本，数据目录 `SB_DATA_DIR` 挂到持久卷上。

要点：

- 副本数固定为 1，不要开自动扩缩容。
- 数据卷只挂给这一个副本，不要多副本共享同一卷。
- 滚动更新期间要保证同一时刻只有一个副本在跑 scheduler。默认的滚动更新会先起新副本再停旧副本，两个副本会同时抢 scheduler 锁，新副本拿不到锁就返回错误、不启动调度循环，推送会短暂中断。要避免这个空窗，用 Recreate 策略，先停旧再起新。

### 方式二：主备 + 文件锁选主

多个副本共享同一个数据卷，靠 `internal/push/scheduler_lock.go` 里的 `AcquireSchedulerLock` 抢锁选主。谁拿到 `dir/scheduler.lock` 的 `LOCK_EX|LOCK_NB` 谁就跑 scheduler，其他副本拿不到锁，`Start` 返回错误，不启动调度循环，只提供 HTTP 服务。

要点：

- 所有副本的 `SB_DATA_DIR` 必须指向同一个共享卷，锁文件路径才会一致。
- 抢不到锁的副本不会自动重试抢锁，进程重启才会重新抢。主副本挂掉后，备用副本不会自动顶上，需要靠编排层拉起新副本或运维介入。
- 共享卷必须是支持 `flock` 的文件系统。NFS 等网络文件系统对 `flock` 的支持视实现而定，用之前先确认。

## 不合规部署的风险

| 不合规做法 | 后果 |
| --- | --- |
| 多副本各自挂独立数据卷，都跑 scheduler | 每个副本按自己的库状态各自推送，同一批用户收到多次推送。 |
| 多副本共享同一数据卷，都跑 scheduler | 两个进程同时写同一个 SQLite 文件，互相争抢文件锁，出现 `database is locked`，写入失败，推送状态错乱。 |
| 滚动更新时新旧副本同时跑 scheduler | 新旧副本抢调度锁，新副本拿不到锁不跑 scheduler，推送中断；若锁文件所在卷被替换，可能出现两个副本都拿到锁，重复推送。 |
| 主备部署但不共享数据卷 | 备用副本没有主副本的推送状态，一旦顶上会按旧状态重复推送。 |

## 排查

- 看日志里有没有 `another scheduler instance holds lock`，有说明当前实例没抢到锁，没跑调度循环。
- 确认所有副本的 `SB_DATA_DIR` 指向的位置。
- 确认副本数。
