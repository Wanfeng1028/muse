# 哨兵-告警升级策略说明

这篇文档讲的是 sentinel 里的告警升级策略怎么配、怎么跑、怎么查。升级策略的意思很简单：一条告警发出去以后，如果一直没人处理，不能就这么算了，得按时间往上抬，先找一线，再找二线，最后找负责人。sentinel 把这件事拆成“升级链”和“升级步骤”两层来做。

## 先看一条完整的配置长什么样

sentinel 的告警规则写在配置文件里，升级部分挂在每条规则下面。下面是一个能直接用的例子：

```yaml
alerts:
  - name: disk_usage_high
    expr: disk_used_percent > 85
    for: 5m
    severity: warning
    summary: "磁盘使用率超过 85%"
    escalation:
      enabled: true
      steps:
        - after: 10m
          notify:
            - channel: email
              to: oncall-l1@example.com
        - after: 30m
          notify:
            - channel: webhook
              url: http://127.0.0.1:9090/sentinel/hook
        - after: 1h
          notify:
            - channel: email
              to: oncall-lead@example.com
          repeat: 30m
          until_ack: true
```

几个字段说清楚：

- `escalation.enabled` 是总开关，false 的时候整条升级链都不走。
- `steps` 是一个数组，按 `after` 从小到大排，`after` 是相对告警触发时刻的等待时间。到点了这一步就发通知。
- `notify` 下面每一项是一个通知目标，`channel` 目前支持 `email` 和 `webhook`。email 要写 `to`，webhook 要写 `url`。
- `repeat` 是重复提醒间隔，配了以后每隔这么久再发一次当前步骤的通知，直到有人确认。
- `until_ack` 为 true 表示必须有人确认才停，false 表示这一步发过一次就往下走。

`after` 和 `repeat` 都支持 `s`、`m`、`h` 三种单位，比如 `30s`、`5m`、`2h`。不写单位默认按秒算，但建议都带上单位，省得后面自己看糊涂。

## 升级是怎么走的

sentinel 收到告警、判断 `for` 持续时间够了之后，会做三件事：

1. 生成一条告警记录，状态置为 `firing`。
2. 如果 `escalation.enabled` 是 true，就把这条告警和它的升级链绑上，记下触发时间。
3. 后台的升级调度器按 `steps` 里每个 `after` 算出该发通知的时刻，到点就发。

有几点要注意。第一步发出去的时候，`after` 是从告警变 `firing` 那一刻开始算的，不是从配置加载那一刻。如果中间告警恢复了，状态变 `resolved`，升级链直接取消，后面还没到的步骤不再发。如果告警又变成 `firing`，重新从头算。

`until_ack: true` 的步骤，只要没人确认，`repeat` 时间一到就重发。确认的动作通过 API 做，见下一节。

## 用 API 查和确认

sentinel 默认监听 9090。下面这些路径都用真实路径，可以直接拿 curl 打。

查看当前所有正在升级的告警：

```
curl -s http://127.0.0.1:9090/sentinel/alerts?state=firing
```

返回是 JSON 数组，每条里有 `name`、`state`、`severity`、`fired_at` 和 `escalation_step`。`escalation_step` 是当前走到第几步，从 0 开始数。

查看单条告警的升级详情：

```
curl -s http://127.0.0.1:9090/sentinel/alerts/disk_usage_high
```

确认一条告警，让升级链停下来：

```
curl -s -X POST http://127.0.0.1:9090/sentinel/alerts/disk_usage_high/ack \
  -H "Content-Type: application/json" \
  -d '{"by":"wanfeng","note":"已经扩容，磁盘降到 60%"}'
```

确认成功返回：

```json
{"name":"disk_usage_high","state":"acked","acked_by":"wanfeng"}
```

手动触发一次升级检查，用于验证配置写对没有：

```
curl -s -X POST http://127.0.0.1:9090/sentinel/escalation/run
```

这个接口会让调度器立刻扫一遍所有 firing 的告警，把到点该发的发出去，不等下一个调度周期。

## 配置改完怎么验证

改完配置别急着上生产，先跑一遍校验：

```
sentinel check -config /etc/sentinel/sentinel.yaml
```

输出 `config ok` 就是没问题。如果 `steps` 里的 `after` 不是递增的，这里会报错，因为升级链必须按时间往后走，不能倒回去。

再看一眼调度器认到的升级链：

```
sentinel escalation list -config /etc/sentinel/sentinel.yaml
```

会把每条告警的每一步、`after`、通知目标列出来。对不上就回去改配置。

## 几个容易踩的坑

- `after` 写重复了，比如两步都是 `10m`，sentinel 会在 `check` 阶段报错，不会静默跳过。
- webhook 的 `url` 没写协议头，比如只写 `127.0.0.1:9090/hook`，发的时候会失败。必须带 `http://` 或 `https://`。
- `repeat` 配得比 `after` 还小没意义，调度器会按 `repeat` 走，但实际提醒会很密，自己掂量。
- 告警恢复后升级链取消，但已经发出去的通知不会撤回。这点要有心理准备。
- `ack` 是按告警 `name` 确认的，同一个 `name` 同时只有一条活跃告警。如果同名告警反复触发，确认的是当前这条。

## 日志在哪看

升级调度器的日志默认在 `/var/log/sentinel/escalation.log`。每一行带时间戳、告警名、步骤序号和动作，比如发通知、跳过、取消。排查“为什么没发”基本看这个文件就够。

要临时调日志级别，启动时加 `-log-level debug`：

```
sentinel run -config /etc/sentinel/sentinel.yaml -log-level debug
```

debug 级别下会打印每一步的到期时间和实际触发时间，方便对时间。
