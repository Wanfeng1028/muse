# 哨兵-限流熔断说明

## 这个模块是干什么的

服务上线以后，最怕两种情况：一种是某个接口被打爆，把整个服务拖死；另一种是下游服务挂了，上游还傻乎乎地一直调它，线程全堵在那儿。哨兵就是干这两件事的：**限流**挡住太多请求，**熔断**挡住坏掉的下游。

代码在 `sentinel` 目录下，核心是 `Sentinel` 类，限流规则放在 `FlowRule` 里，熔断规则放在 `DegradeRule` 里。

## 限流怎么配

限流的核心参数有三个：

- `resource`：资源名，一般就是接口路径，比如 `/api/order/create`
- `count`：阈值，每秒允许多少个请求
- `grade`：限流类型，`FLOW_GRADE_QPS` 是按每秒请求数限，`FLOW_GRADE_THREAD` 是按并发线程数限

举个例子，给下单接口配个每秒 100 次的限制：

```java
FlowRule rule = new FlowRule();
rule.setResource("/api/order/create");
rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
rule.setCount(100);
FlowRuleManager.loadRules(Collections.singletonList(rule));
```

配上以后，第 101 个请求进来会抛 `FlowException`。业务代码里要接住这个异常，返回“请求太频繁，稍后再试”，别让它冒到最外层变成 500。

如果不想抛异常，可以用 `SphU.entry` 的 try-catch 包一下：

```java
try (Entry entry = SphU.entry("/api/order/create")) {
    // 正常业务
} catch (BlockException e) {
    // 被限流了，走降级逻辑
}
```

## 熔断怎么配

熔断盯的是“下游是不是已经坏了”。规则参数：

- `resource`：资源名
- `count`：触发熔断的阈值
- `grade`：熔断策略，`DEGRADE_GRADE_RT` 是平均响应时间超了就断，`DEGRADE_GRADE_EXCEPTION_RATIO` 是异常比例超了就断
- `timeWindow`：熔断后多久进入半开状态，单位秒
- `minRequestAmount`：最少要统计多少个请求才开始判断，防止样本太少误判

举个例子，调支付服务的接口，平均响应时间超过 500 毫秒就熔断，断 10 秒：

```java
DegradeRule rule = new DegradeRule();
rule.setResource("callPaymentService");
rule.setGrade(RuleConstant.DEGRADE_GRADE_RT);
rule.setCount(500);
rule.setTimeWindow(10);
rule.setMinRequestAmount(20);
DegradeRuleManager.loadRules(Collections.singletonList(rule));
```

熔断期间请求直接走 `BlockException` 分支，不会真的去调下游。10 秒后进入半开，放一个请求过去试，成功就恢复，失败就继续断。

## 配置项从哪来

生产环境一般不用硬编码，配置从配置文件读。文件路径 `sentinel/config/flow-rules.json`，格式长这样：

```json
[
  {
    "resource": "/api/order/create",
    "grade": "FLOW_GRADE_QPS",
    "count": 100
  },
  {
    "resource": "callPaymentService",
    "grade": "DEGRADE_GRADE_RT",
    "count": 500,
    "timeWindow": 10,
    "minRequestAmount": 20
  }
]
```

启动时调 `RuleLoader.loadFromFile("sentinel/config/flow-rules.json")` 加载。改完配置不用重启，调 `RuleLoader.reload()` 重新读一遍就生效。

## 看监控数据

实时数据在 `/sentinel/metrics` 这个接口，返回 JSON，字段有：

- `resource`：资源名
- `passCount`：通过的请求数
- `blockCount`：被拦的请求数
- `avgRt`：平均响应时间，单位毫秒
- `exceptionCount`：异常数

命令行的用 curl 拉一下就行：

```bash
curl http://localhost:8080/sentinel/metrics
```

想看某个资源的历史趋势，`/sentinel/metrics/history?resource=/api/order/create&minutes=30`，返回最近 30 分钟每分钟的统计。

## 几个容易踩的坑

**资源名写错**。`SphU.entry` 里写的字符串和规则里的 `resource` 必须一模一样，差一个字符规则就不生效，而且不报错，很难查。

**阈值拍脑袋定**。限流阈值要按压测结果来，不是随便写个 1000。定太高等于没限，定太低正常用户都被拦。

**熔断时间窗口太短**。`timeWindow` 设 1 秒，下游还没缓过来就放请求进去，等于没断。一般至少 5 秒起步，看下游恢复速度调。

**忘了处理 BlockException**。限流熔断抛的异常不接住，用户看到的是 500 错误页，体验很差。该返回友好提示就返回友好提示，该走兜底逻辑就走兜底逻辑。

## 改规则的正确姿势

线上改规则不要直接改配置文件然后 reload，容易手抖。建议流程：

1. 先在测试环境改，压测验证阈值合不合适
2. 确认没问题再同步到生产配置
3. reload 之后立刻看 `/sentinel/metrics`，观察 `blockCount` 有没有异常飙升
4. 如果拦太多了，赶紧把阈值调回去再 reload

规则是热生效的，改错了马上能改回来，但中间那几秒被拦的真实用户是实打实受影响的，所以别在高峰期折腾。
