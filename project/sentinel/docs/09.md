# 哨兵-多实例规划

## 这篇讲什么

哨兵（Sentinel）是单实例的。一个进程管一份规则、一份内存统计、一份熔断状态。但生产环境里经常要多实例跑，这篇就说清楚多实例下该怎么规划，哪些东西能共享，哪些必须各管各的。

## 为什么要多实例

三种常见场景：

1. 流量太大，一个哨兵进程的 CPU 顶不住，统计和规则匹配都是算力活。
2. 服务部署在多个机房，每个机房就近接入一个哨兵，省跨机房延迟。
3. 想灰度，一部分流量走新规则，另一部分走旧规则，两套实例并行。

这三种诉求不一样，规划方式也不一样，下面分开说。

## 配置项怎么拆

哨兵的核心配置走 `application.yml`，多实例要拆的是这几项：

```yaml
sentinel:
  app:
    name: order-service
    type: 1
  transport:
    dashboard: 127.0.0.1:8080
    port: 8719
    heartbeat-interval-ms: 10000
  eager: true
  web-context-unify: true
```

`transport.port` 是重点。单机跑一个实例，用默认 8719 就行。同一台机器上跑多个实例，每个实例必须给不同的 `transport.port`，比如 8719、8720、8721。端口撞了，后启动的直接报端口占用，起不来。

`app.name` 决定这个实例属于哪个应用。同一个应用的多个实例，`app.name` 保持一致，这样控制台里能看到聚合数据。不同应用才用不同 `app.name`。

`transport.dashboard` 指向控制台地址。多机房的话，每个机房指向自己那台控制台，别让跨机房心跳拖慢启动。

## 规则数据怎么同步

规则有两种存法：

第一种，规则写在代码里，用 `FlowRuleManager.loadRules(rules)` 加载。这种最省事，每个实例启动时自己加载，不需要外部依赖。缺点是改规则要发版。

第二种，规则存在控制台或配置中心，实例通过心跳从控制台拉。这种改规则不用发版，但要保证控制台高可用。控制台挂了，新实例拉不到规则，老实例还能用内存里已有的规则继续跑。

多实例下，推荐第二种。规则集中在控制台改一次，所有实例几分钟内同步到位。但要注意：控制台推送规则是异步的，实例之间生效时间会有秒级差异。如果你的业务对规则切换时间很敏感，比如风控场景，那就得接受这个差异，或者把规则做成定时轮询加本地缓存兜底。

## 统计和熔断状态不能共享

这一点必须说清楚：每个实例的统计是独立的。

`ClusterNode` 里的 QPS、线程数、响应时间，都是本实例自己算出来的。实例 A 不会知道实例 B 处理了多少请求。这意味着：

假设规则是“QPS 超过 100 就限流”，你起了 3 个实例，实际总 QPS 到 300 才会每个实例都触发限流。如果你想要的是全局 100，那就得用集群流控。

集群流控要额外部署一个 token server，配置项是：

```yaml
sentinel:
  flow:
    cluster:
      mode: server
```

客户端这边：

```yaml
sentinel:
  flow:
    cluster:
      mode: client
      server-host: 127.0.0.1
      server-port: 18730
```

token server 是单点的，要做高可用得自己想办法，哨兵本身不带 token server 的集群方案。所以如果只是想限流总量，又不愿意维护 token server，还有个土办法：把阈值按实例数除。3 个实例，全局想限 100，每个实例配 34。缺点很明显，实例数一变，规则就得跟着改。

## 控制台里的实例列表

控制台机器列表页面能看到当前应用下所有上报心跳的实例。每个实例一行，显示 IP、端口、健康状态。

这里有个坑：`transport.port` 相同的两个实例，控制台会认为是同一个，后上报的覆盖先上报的。所以前面强调端口必须错开。

如果某个实例下线了，心跳停了，控制台会在 `heartbeat-interval-ms` 的几倍时间后把它标成不健康，但不会自动删掉记录。要清理得手动在控制台操作。

## 部署上的建议

同机多实例，端口规划好，别用默认值一把梭。容器环境里，每个 Pod 一个实例，端口可以用默认 8719，因为 Pod 之间网络隔离，不会撞。

多机房，每个机房一套控制台，规则在两边分别配，或者用配置中心统一推。别让机房 A 的实例去连机房 B 的控制台，跨机房网络抖一下，心跳断了，规则就拉不到了。

实例数变动频繁的话，集群流控的 token server 会成为瓶颈，因为所有实例都要连它。这种情况下，宁可每个实例单独限流，阈值除以实例数，简单可靠。

## 一个完整例子

订单服务，3 个实例，部署在两台机器上：

机器 A 跑两个实例，`transport.port` 分别是 8719 和 8720。
机器 B 跑一个实例，`transport.port` 是 8719。

三个实例的 `app.name` 都是 `order-service`，`transport.dashboard` 都指向同一台控制台。

规则用控制台配置，推送到三个实例。限流规则是每个实例 QPS 50，加起来 150。

启动命令里带上端口参数：

```
java -jar order-service.jar --sentinel.transport.port=8720
```

这样机器 A 的第二个实例就会用 8720，不会和第一个撞。

控制台里能看到三个实例，健康状态都是绿的。改规则后，三个实例陆续生效，顺序不保证，但最终都会同步。
