# 哨兵-探针排障手册

这篇文档讲的是哨兵（Sentinel）和探针（Probe）之间出问题时怎么查。假设你已经按部署文档把两边都跑起来了，现在某块数据对不上、或者探针压根不上报，按下面的顺序往下撸。

## 一、先搞清楚谁负责什么

哨兵是常驻进程，负责收探针上报、算规则、发告警。探针是嵌在业务进程里的客户端，负责采集指标、定期往哨兵推。两边通过 HTTP 通信，探针主动推，哨兵被动收。所以链路上任何一段断了，现象都是"探针不上报"或"数据延迟"。

排障第一步永远是确认边界：是探针没发，还是发了哨兵没收到，还是收到了但算错了。不要一上来就翻哨兵日志，先看探针。

## 二、探针侧排查

探针的配置在 `probe/config/probe.properties`，关键项：

- `probe.sentinel.address`：哨兵地址，格式 `host:port`，不要带 `http://` 前缀，带了会连不上。
- `probe.interval.seconds`：上报间隔，默认 10。改成小于 1 的值探针会拒绝启动并打日志。
- `probe.metric.batch.size`：单次上报的指标条数上限，默认 200。业务指标特别多的时候要调大，否则会被截断。
- `probe.log.level`：日志级别，排障时先调到 `DEBUG`。

探针日志默认在 `probe/logs/probe.log`。搜这几个关键字：

- `connect refused`：哨兵没起，或者地址写错，或者防火墙挡了。
- `report timeout`：连上了但哨兵处理慢，或者网络抖动。先看哨兵那边有没有堆积。
- `batch truncated`：说明指标条数超了 `probe.metric.batch.size`，调大它。

想手动确认探针到哨兵的链路通不通，直接在探针机器上敲：

```
curl -v http://<sentinel-host>:<port>/api/v1/probe/ping
```

正常返回 `{"status":"ok"}`。返回 404 说明哨兵版本和探针对不上，检查两边版本号。连不上就是网络或哨兵没起。

## 三、哨兵侧排查

哨兵配置在 `sentinel/config/sentinel.properties`，排障相关的：

- `sentinel.http.port`：监听端口，默认 8080。探针地址里写的端口必须和这个一致。
- `sentinel.probe.timeout.ms`：处理单次上报的超时，默认 3000。探针报 timeout 时先看这个值是不是太小。
- `sentinel.rule.reload.seconds`：规则重载间隔，默认 30。改了规则不生效，等一个周期再看。
- `sentinel.storage.path`：数据落盘路径。磁盘满会导致上报静默失败，日志里有 `write failed`。

哨兵日志在 `sentinel/logs/sentinel.log`。查上报是否到达，搜 `probe report received`，后面会跟探针的标识。如果探针说发了、这里搜不到，那就是网络层丢包或端口不通，回到第二步用 curl 验证。

查规则是否命中，搜 `rule matched`，会打印规则名和命中的指标。如果数据进来了但没告警，多半是规则条件写错了，或者指标名对不上。指标名大小写敏感，探针发的是 `cpu_usage`，规则里写 `CPU_USAGE` 就不会命中。

## 四、常见现象对照

**现象：探针启动就退出，日志里 `invalid interval`。**
`probe.interval.seconds` 被设成了 0 或负数，改回正整数。

**现象：哨兵收到了上报，但监控面板没数据。**
先确认 `sentinel.storage.path` 所在磁盘没满，再确认面板查的时间范围和探针上报的时间对得上。跨时区部署时探针和哨兵要统一时区，否则数据会落在错误的时间桶里。

**现象：告警延迟很久才发。**
看 `sentinel.rule.reload.seconds`，规则改完要等这个周期。另外探针的 `probe.interval.seconds` 也会引入延迟，两边加起来就是最坏情况下的告警延迟。

**现象：只有部分指标缺失。**
大概率是 `probe.metric.batch.size` 截断了，日志里有 `batch truncated`。调大之后重启探针。

## 五、健康检查接口

哨兵暴露了两个接口用于排障：

- `GET /api/v1/health`：返回哨兵自身状态，正常是 `{"status":"up"}`。
- `GET /api/v1/probe/status`：返回最近一次各探针上报的时间戳。某个探针的时间戳很旧，说明它掉线了。

这两个接口不需要鉴权，方便在探针机器上直接 curl。

## 六、还是查不出来怎么办

把探针日志调到 `DEBUG`，哨兵日志也调到 `DEBUG`，复现一次问题，然后按时间戳对齐两边的日志。探针日志里每次上报会有 `report seq=<n>`，哨兵收到同一条会有 `probe report received seq=<n>`。用 seq 号对，能直接看出是哪一跳丢的。对不上 seq 就是网络问题，对得上但后续没处理就是哨兵内部逻辑问题，把两段日志一起提给维护者。
