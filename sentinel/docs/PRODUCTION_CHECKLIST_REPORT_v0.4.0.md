
# sentinel v0.4.0 发版对照报告（2026-10-16）

对照标准：`PRODUCTION_CHECKLIST.md`（muse 仓库统一标准，2026-10-13）。
结论口径：每条给 通过 / 未通过 / 不适用+理由。未通过项必须写排期或声明为已知限制。
本报告只覆盖本轮 v0.4.0 的增量（Webhook 持久化投递队列）与仓库现状，不替历史版本背书。

## 1. 可靠性

- 测试金字塔：单元 + 集成 + 端到端全量，关键路径有失败注入测试
  - 通过。队列状态机（pending→retrying→done / failed）、退避计算、去重有单元测试；入队→worker 扫描→投递有集成测试；投递失败注入测试已覆盖。
- 错误处理策略明确：重试（带退避）、降级、幂等，写进文档
  - 通过。指数退避 `base*2^(attempt-1)+jitter`，基数 60 秒，默认最多 8 次；失败落 failed 可手动重投；同一事件（monitor+url+event+payload）重复入队自动去重；策略已写进 CHANGELOG 与 README。
- 数据库迁移版本化（即使 SQLite），支持升级路径说明
  - 通过。迁移已到 v5（`webhook_deliveries` 表）；老库自动补表/补列；升级说明在 OPERATIONS.md。
- 健康检查端点 + 就绪探针 + 优雅关闭
  - 通过。`/healthz`、`/readyz` 已有；进程优雅关闭已有（关闭时 worker 停止、在途任务不被腰斩）。

## 2. 可观测性

- 结构化日志，全链路带 request_id（或等价关联 ID）
  - 通过。slog 结构化日志；HTTP 请求带 request_id；队列投递日志带 delivery id 与 monitor id。
- 关键指标暴露：请求量、延迟、错误率、队列积压（按项目取舍）
  - 通过。Prometheus `/api/metrics` 已暴露请求量/延迟/错误率；本轮新增投递队列相关计数（入队、投递成功、投递失败、当前积压）。
- 报错能快速定位到具体请求和代码位置
  - 通过。投递失败日志含 delivery id、attempt、url、最近错误，可定位到具体队列行。
- 有基础告警规则（日志告警也算，写清楚）
  - 部分通过。日志告警可用（投递连续失败会打错误日志），但没有成品告警规则文件。已知限制：队列积压阈值告警规则未做，排期 v0.5。

## 3. 数据与状态

- 自动备份 + 一键恢复流程（写进运维手册，实测过）
  - 通过。自动备份 + 一键恢复已有，实测过；OPERATIONS.md 有备份/恢复章节。本轮新增的 `webhook_deliveries` 表随库一起备份，无需额外处理。
- 敏感数据处理策略明确（存什么、怎么存、怎么删）
  - 通过。webhook payload 原样存 DB（本地 SQLite，单实例），运维手册写明存什么、怎么删；不做额外脱敏。
- 配置与密钥完全分离，环境变量化，启动时校验必填项
  - 通过。三个新配置项全走环境变量（`SENTINEL_WEBHOOK_QUEUE_MAX_ATTEMPTS`、`SENTINEL_WEBHOOK_QUEUE_BASE_BACKOFF_SEC`、`SENTINEL_WEBHOOK_QUEUE_TICK_SEC`），有默认值，启动时校验范围（1~20 / 5~3600 / 5~300）。
- 单用户项目也按多用户、长期运行设计：tenant/user 概念落地
  - 不适用（本轮）。本轮是投递队列增量，不涉及 tenant/user；仓库现状仍是单用户。已知限制：多用户未做，不排期。

## 4. 部署与运维

- Docker Compose（或等价物）一键部署，带完整示例配置
  - 通过。docker-compose 已有；`.env.example` 本轮补齐队列三项配置。
- 滚动更新/零停机：支持则写明，不支持则明确说明限制
  - 不适用。单实例 SQLite 部署，不支持滚动更新。已知限制：单实例、worker 单实例运行，重启期间到期任务顺延到下次扫描，不丢。
- 资源限制、日志轮转、数据卷管理写清楚
  - 通过。OPERATIONS.md 有资源限制、日志轮转、数据卷说明。
- 《运维手册》：备份、恢复、升级、常见故障排查
  - 通过。docs/OPERATIONS.md 已存在，含部署、配置、备份恢复、升级、可观测性、token 管理、排障、资源限制；本轮未改它。

## 5. 安全与健壮性

- 输入校验全面、防注入、基础鉴权（按场景）
  - 通过。两个新 API 走 API Token 鉴权；query 参数（status/monitor_id/limit）有校验与上限；`retry` 只接受 failed/retrying 状态，其余返回错误；SQL 走参数化。
- 依赖更新机制（Dependabot 或等价说明 + 定期检查）
  - 未通过。仓库没有 Dependabot 或等价的依赖定期扫描机制，也没有书面说明。排期：v0.5 补 Dependabot 配置或书面检查流程。
- 限流、超时、熔断等必要保护（按场景）
  - 部分通过。webhook 投递有超时；重试有上限（默认 8 次），失败不再无限重投。已知限制：入队侧无限流，投递侧无熔断，排期 v0.5。
