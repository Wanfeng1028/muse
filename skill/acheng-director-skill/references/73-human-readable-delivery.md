# 人类可读交付视图合同

本合同定义 Acheng 的用户-facing 输出层。它不替代 production.json、`.image.txt`、`.h3.txt`、index.json 或质量门；它把同一份真值源按导演工作流重新编排，让用户先理解项目，再复制提示词，最后处理上传与验收。

## 核心原则

1. **先结论，后证据**：开头先给项目状态、总时长、当前阶段、可直接使用的文件和阻塞项；不要让用户先读原始 JSON。
2. **先路线，后细节**：先用一张生产路线表说明剧本、资产、分镜、表演/动作/VFX、视频提示词和质检各自的状态，再展开正文。
3. **一张卡只回答一个动作**：资产卡回答“生成什么、用途是什么、需不需要参考图”；段落卡回答“这一段拍什么、用哪种 H3 模式、上传什么”；质检卡回答“能否提交、还差什么”。
4. **复制区与说明区分离**：展示载体按[109 模式合同](109-segment-delivery-modes-v4.md)和[114 绑定合同](114-reference-binding-delivery-v4.3.6.md)。自动模式直接展示逐段操作卡，完整正文保存在独立文件；交互模式展示当前段完整代码块和操作卡。任何模式都不得摘要、截断或压缩文件正文；Ref2VA 动态词数和全部创作细节不变。
5. **人名与状态可见，内部 ID 不扰民**：用户视图显示角色名、资产名、状态、版本和 Shot/Segment 名称；CHAR_、SCENE_、E 编号、Previs 编号只在括号内作为可选追踪信息，绝不替代自然语言描述。
6. **亮点要被看见**：在每个段落卡的“导演意图”中明确写出本段的因果表演链、镜头路径、切镜承接、尾态、保留/排除规则，以及引用的灵动表演、巨构、VFX 或清洁流程；不要用“已优化”一笔带过。
7. **状态必须诚实**：`READY_TO_SUBMIT` 只表示提示词与必要输入齐全，不表示媒体已经生成或画面已经通过人工验收；缺参考图时显示 `DRAFT_MISSING_REFERENCES`，外部模型能力未核实时显示 `UNVERIFIED`。

## 默认章节顺序

完整制作或视频分支默认按下面顺序在对话中呈现。局部任务跳过不存在的章节，但不改变章节名称和字段含义。

### 0. 导演总控台

```text
项目：<项目名>
交付范围：<full_production / prompt_only>
状态：<可提交 / 待参考图 / 需修复 / 未完成人工验收>
总时长与帧率：<秒数> · <fps>
模型：GPT Image 2/2.5（资产） · MiniMax H3（视频）
本次可先做：<最短可执行动作>
阻塞项：<没有则写“无”>
```

状态行下面给出不超过三句的创作摘要：主线冲突、视觉锚点、当前最重要的连续性约束。

### 1. 一页生产路线

| 阶段 | 交付物 | 状态 | 用户下一步 |
|---|---|---|---|
| 剧本/叙事 | 主线、支线、伏笔、人物弧光 | 已确认/草案/跳过 | 审阅或确认 |
| 资产 | 角色、场景、道具、特效、关键帧 | 就绪/待参考图 | 先生成缺失资产 |
| 分镜 | ShotSpec、时间轴、运镜 | 已锁定/需修复 | 审阅切片边界 |
| 表演/动作/VFX | 因果动作链、声音、效果阶段 | 已编译/不适用 | 关注关键节拍 |
| 视频 | 每段独立 H3 正文 | 可复制/待输入 | 上传并提交 |
| 质检 | 机器门、人工验收边界 | PASS/UNVERIFIED | 生成后逐帧检查 |

### 2. 剧本与叙事（存在时）

先给“一句话冲突”和“时间线/段落弧”，再给主线、支线、明线/暗线、人物知情差和伏笔回收。不要把完整结构化登记簿放在正文首屏；需要机器数据时链接或另列“机器真值”。

### 3. 角色、场景与资产目录

先给目录表，再逐项给资产卡。角色身份资产必须显式写“四视图角色身份基准：正面全身、背面全身、侧面全身、正脸头肩近景”；角色名和状态写在卡片标题中。每张卡至少包含：

```text
资产：<名称> · <状态/版本>
用途：<身份/服装状态/场景/道具/特效/关键帧>
生成模式：<GENERATE / EDIT / REBUILD / MIXED>
参考图：<无需参考图 / 必须上传图1、图2...>
保留：<身份、结构、材质或构图>
不继承：<不应带入的姿态、光线、文字、网格或旧状态>
```

随后给唯一的 `*.image.txt` 正文链接；交互制作时展开完整复制区，自动文件模式不重复长正文。图片模型只看到自然语言；代号不得替代描述。清洁流程仍须完整落入正文，操作说明不能混入模型输入。

### 4. 分镜与段落地图

用一张表让用户先看完整闭合时间轴：

| 段落 | 全局时间 | 时长 | H3 模式 | 镜头事件 | 导演意图/尾态 | 参考输入 |
|---|---:|---:|---|---|---|---|

表后再按段落展开 Shot 1、Shot 2……。每个 Shot 只写可视事件、人物状态、镜头路径、声音节拍和切点；132 运镜编号只能作为括号索引，必须同时写出实际方向、距离、速度和目标。

### 5. 表演、动作与视效亮点

只展示本项目真正启用的卡片。每张卡用同一顺序：

`人物目标 → 社交策略/潜台词 → 触发事实 → 可见动作（预备/重音/跟随/收势） → 语气/声音节拍 → 切镜承接 → 连续尾态`。

打戏增加 `攻击 → 防守 → 接触结果 → 受力传递 → 恢复权限`；视效增加 `起源 → 形态/质量 → 碰撞 → 光照 → 衰减`；巨构增加比例参照、遮挡层和质量支撑。没有启用的模块不要硬填。

### 6. GPT Image 2/2.5 复制区

每个资产先给一行“用途/参考/提交状态”，再给完整提示词。默认角色资产的四视图布局必须在这一行和正文中同时出现。正文结束后不得附解释、参数建议或额外文字，避免用户把说明一并喂给图像模型。

每个资产卡的复制区前必须紧邻一个“参考图上传助手”，按实际上传顺序列出：槽位编号、可上传的真实文件链接、用途、必须保留、禁止继承、缺图时先生成的依赖资产。明确写出“先上传参考图，再复制提示词”，并在卡片末尾给提交前检查：文件可打开、顺序与 `Reference image N` 一致、没有把导航说明贴进提示词。无参考图时明确写“无需上传，可直接提交”，不能让用户猜测。

### 7. MiniMax H3 复制区

每个 Segment 使用独立卡片：

```text
SEGMENT <编号> · <时长> · <I2VA/FL2VA/L2VA/Ref2VA/T2VA>
起始状态：<本段第一帧或文字起始状态>
参考输入：<每张图的用途、保留和排除>
导演意图：<因果表演、镜头路径、切点和尾态>
提交状态：<可复制 / 待素材 / 未核实执行能力>
```

交互模式在卡片下面直接展开当前完整 `.h3.txt` 正文；自动模式给完整文件链接而不重复长正文，但必须直接呈现每段操作卡。正文独立声明主体/场景/状态、时间码、对白、声音、音乐和参考关系；不能被摘要替代或缩减。

每个 Segment 的正文链接或复制区前紧邻独立上传卡：实际媒体或明确未绑定、版本、Subject/speaker、用途、Shot/帧窗、保留/排除、顺序、缺项及下一步。只有明确 T2VA 且未声明引用需求时写无需上传；缺素材的引用模式写待素材，不假定已上传。

### 8. 上传清单与验收

先按生成顺序列出“先生成什么、批准哪个版本、再上传到哪一段”，再列每段素材表。最后分开报告：

- 机器合同：字段、时长、代号消解、引用顺序、哈希和链接是否通过。
- 人工画面：身份稳定、四视图一致、动作自然、碰撞/材质、声音和最终尾态仍待真实生成后检查。

## 紧凑模式与机器模式

用户说“简版/只要提示词”时保留总控台、资产/段落卡、复制区和阻塞项，隐藏长篇理论与机器 JSON；用户说“机器交付/审计”时附上 `production.json`、`index.json`、`audit.json` 和完整字段。没有明确要求时使用本合同的完整人类可读视图。

## 禁止的表达退化

- 不以一整段 JSON 代替导演总控台。
- 不以摘要取代独立文件中的完整正文；自动模式允许正文留文件，但不允许省略逐段操作卡。
- 不把 `subject_definitions`、`retention_analysis`、`detailed_description` 等字段标题当作唯一解释；字段之外必须给中文用途和上传动作。
- 不在资产名称文件混入“提示词、参考图、状态”等说明性噪声；说明放在资产卡和 `UPLOAD.md`。
- 不写“同上、沿用前段、见角色设定”来省略独立提示词；这条只允许出现在人类可读摘要，不能进入模型正文。
- 不把“已通过”写成“已生成”；机器验收和真实媒体验收必须分开。
