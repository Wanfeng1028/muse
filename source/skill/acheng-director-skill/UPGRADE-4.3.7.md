# Acheng Director 4.3.7｜定向引导与真实参考接力

基线为用户提供的 acheng-director-v4.3.6-integrity.zip，在新目录开发。原 ZIP 与已安装 skill 不变；未使用子代理或 skill-creator，未调用收费媒体模型、上传平台或执行公开发布。

## 对原结构的判断

原包有实质的创作能力与工程合同，不能因为工序多就判定为无效。原本已有情绪触发、表演因果、摄影适用条件和部分反问；欠缺的是把这些知识稳定地放到当前决定之前，告诉宿主先读哪项事实、排除哪条路、把结果放到哪个既有字段。

| 原机制 | 实际作用 | 不能保证的事 |
|---|---|---|
| 分阶段、按模块读取 | 减轻一次处理所有专业问题的压力 | 不提升底座模型固有推理上限 |
| 完整文件、partial、cursor、commit | 处理单次输出长度和中断，完整保存可继续的工作 | 不允许用短摘要充当完成稿 |
| 唯一 production、owner、revision | 避免多模块抢写、旧版本覆盖和交接不清 | 不自动证明自然语言内容正确 |
| 格式、时间、批准、哈希与回读门 | 守住可计算结构、来源与交付一致性 | 不证明生成画面的审美、表演与物理质感 |

本版保留上述机制。动态详细度、模式锁、图像七步、动作七层及 timing、STYLE_MOTHER、四视图身份、相邻复核、批准记录、原子提交与恢复均沿用原合同。

## 引导怎样安排

新增[总入口 115](references/115-directed-decisions.md)及七份模块指南，共 26 个问题场景。各模块入口、registry、dispatch step 和 workflow node 均可到达对应指南。不建立第八个 owner，不改变生产 schema。

| 模块 | 本版具体引导 |
|---|---|
| story | 动作是否改变具体事实；知情来源；台词的行动目的；既有道具与人物选择 |
| shots | 必须看清的部位；遮挡原因；是否真的需要运动；越轴依据；时长容纳不下时如何交回 |
| performance | 当前触发；要展示／隐藏的态度；可见部位与伤势筛选；接触／落空的因果链；呼吸与台词冲突 |
| assets | 不同图的保留／排除；关键帧逐项取材；未知背面与重建；身份／状态／图号交接 |
| effects | 接触被遮挡时修哪一层；尺度参照是否独立；风格化规则如何保留 |
| model | Subject 与 Picture 分工；四视图不是四个人；关键帧范围；旧姿态和未来状态污染；用户实际上传哪张图 |
| continuity | 前后状态改变发生在哪一镜；省略是否有批准依据；版本与状态区别；从有效提交恢复 |

例如摄影指南先问“当前中景是否已经看清两只交接的手”，答案为是且没有揭示／跟随需求时，固定镜头可以成立；需要运动才查相关运镜条目，再核对该移动会不会裁掉关键部位。这比每镜强制找两个编号辩论更容易执行，也保留了需要比较时的取舍空间。

问题不是每个位置重复一遍。只对当前困难运行对应小节，已确定且输入未变的决定直接继承。结果写回原字段，必要依据放进已有 evidence。无需交出长篇思考过程、增加全局问卷或手写第二套自证 YAML。缺少关键事实时给出具体缺项；不能靠猜测补齐批准、素材或已锁定剧情。

## 为什么保留混合资料库

Markdown 适合解释条件、分支、反例和知识之间的关联。JSON 适合稳定编号、筛选、引用和机械检查。真实图片／视频承担文字无法替代的视觉参照。生产 JSON 则保留当前项目的已接受事实。

本版在现有资料库上增加 Markdown 决策层，没有把运镜、情绪、术语、源文件或媒体改成另一套平行手册。132 项运镜与白模、原始及扩展情绪配方、动画术语与源文件哈希继续保留。指南先缩小问题再路由资料，不要求弱模型从全库自行找出答案。

## 修复了哪些真实断点

1. 原 H3 附带资产分支虽然已解析依赖并导出 .image.txt，但交付条目只有参考数量与缺项文字，未附这些资产自己的图片副本和逐图上传映射。本版与独立资产编译器共用 asset_delivery，把实际媒体、槽位、来源、保留／排除、版本及独立卡片一并交付。
2. 原资产解析以文件存在为主。本版复用已有媒体检查，拒绝提示词文本冒充图片，核对基础文件签名与已有批准哈希；approved 资产缺哈希不能视为可信输入。未解决项保留草案，不自动跳到无参考生成。
3. 缺少第 1 张图而第 2 张存在时，保持原图号；不把第 2 张悄悄改成第 1 张。缺项保留其用途、对象、保留／排除和补齐动作。
4. 新卡片、正文、实际媒体、来源卡与 revision 都能从导出文件回读核对；卡片改动、媒体被替换、整项资产遗失不能沿用通过结果。
5. 聊天紧凑视图保留资产上传卡与完整正文链接，避免再次展开全部资产长正文；完整文件和完整交付视图仍保留。

## 图片究竟怎样被使用

| 图片 | 资产制作阶段 | H3 阶段 |
|---|---|---|
| 人物四视图 | 状态图／关键帧的身份来源；四格视为同一人 | 可作为一个人物 Subject 的来源，排除板式与中立站姿 |
| 状态版本图 | 保留已发生的服装／伤势变化 | 仅作用于相应镜头或帧窗，不把未来损坏带入开场 |
| 场景图 | 保持地标、入口及通行结构，必要时重建新视角 | 环境内容参考；不无条件锁死摄影机 |
| 道具／载具图 | 保持形状、操作部件和比例 | 对应用途的内容参考，不继承原持有人或未来破损 |
| 单幅关键帧 | 汇合所需批准身份、场景、道具与状态 | 首帧／尾帧／中间锚点，说明到达与离开，不冻结整段 |
| 接触表／灰模 | 布局和相位规划；需要单帧时制作可追溯独立资产 | 按批准用途作规划参考，不当真实身份或单个首尾帧 |
| 风格母图 | 适用资产提示词最后的风格槽 | 只有本段确有直接需求才上传，不把全库一股脑上传 |
| 特效形态图 | 形态、纹理及尺度提示 | 不替代动作过程、时间及因果字段 |

“有资产”不等于“每段都应上传”。assets 提供批准文件和用途，shots 提出当前镜头需求，model 绑定本段局部标签，continuity 核对作用时机。资产卡编号与 H3 段编号分别属于各自请求。Subject 是对象身份，不增加图片槽位。

## 使用与验收

原 compile_assets.py 与 compile_h3.py 调用方式保留。独立资产包新增 ASSET_ID.upload.md，H3 附带资产新增 ASSET_ID.asset-upload.md；视频段继续使用 SEG.upload.md。

    python scripts/asset_delivery.py output/assets-revision-01 --production production.json
    python scripts/h3_delivery.py output/video-revision-01 --production production.json

资产校验返回 0=本地合同通过、2=草案不可提交、1=失败。H3 联合回执分开报告视频段状态与 asset_prompt_delivery；不因为存在一项待制作资产草案就否认另一段已正确绑定批准媒体，也绝不把草案当作已完成图片。

当前机器证据以 [4.3.7 最终包验收](reports/package-acceptance-v4.3.7-final.json)和 [4.3.7 测试记录](reports/tests-v4.3.7.txt)为准。旧版报告仅为历史。本版只增加一个测试文件、五个验收用例，覆盖本次行为与复现的断点。

验收边界：未做不同弱模型的实际对照生成，未生成或上传影片，不能宣称艺术提升已被实证。机器通过证明代码、路由与引用合同成立；媒体签名和哈希不等于已经看懂画面。平台能力、最终画面和声音质量继续保持 UNVERIFIED，直到取得相应真实证据。
